# Official browser source

`@miy/official-suite-web` exposes metadata only: twelve owned app manifests, ordered `OFFICIAL_APP_MANIFESTS` and `OFFICIAL_HELP_GUIDES`. The shared app contract owns membership, canonical routes and admission identity. `@miy/official-suite-web/modules` assembles the actual business modules for the independent official UI artifact. The portal imports manifests and document-navigation descriptors; it does not import this full module entry.

All twelve implementations belong here: PMS, Docs, Files, Mail, Community, Whiteboard, Diagrams, Bento, Planner, Meeting, Video Chat and Recording. Each `<app>/module` owns its existing routes/sidebar/providers/background sources. Public `<app>`, `public-api` and picker entries keep existing same-object compatibility exports under the old web app paths. Private source imports remain owner-restricted. Files uses the public common Chatbot experience; business apps never select provider credentials or bypass the product AI gateway.

`/summaries` collects each app's narrow `summary-api.ts` public entry for the existing Docs/Meeting/Planner/PMS read clients and DTOs used by platform Home. It does not import private API implementations across app owners or expose business components. Runtime view changes can be released in the official artifact without rebuilding/restarting the portal; shared summary API/SDK contract changes remain platform-impacting. Metadata, common locale catalog and generic UI primitives remain reviewed shared dependencies.

Common AuthContext, API/time/locale helpers, pickers, generic Markdown editor, realtime, form/media/date/directory/UserPicker, browser routing/deployment and Chatbot implementations belong to [platform-web](../platform-web/README.md). Neither library may import an application root. Each trusted first-party document initializes its single existing auth/bootstrap/i18next/live realtime lifecycle. Authorization and shared state remain on the server.

Community's public editor exports the same generic Markdown primitive from platform-web; it has no Community API dependency and accepts upload/URL/copy callbacks. This lets platform admin preserve editing without compiling Community views. Its existing names/messages remain compatible. Business app messages still belong to their owner; the shared root composes the existing catalog without eagerly importing screens.

The calendar source is business-owned: event DTO/API/reducer/hook, FullCalendar wrapper/adapter and scoped CSS aggregate Meeting/PMS/Planner. Official startup imports this CSS; portal business view bodies are excluded by the platform Vite boundary. Generic holiday/color/time primitives remain common.

Fixed assets have one owner: `public/recording-sync-sw.js` and `public/help/pms/user-guide.html`. `vite/fixed-assets.mts` is installed only in the official Vite build. It serves/emits exact bytes with fixed names and supports the official dev namespace; core Vite forwards the original public URLs to that owner. Recording registration keeps the original URL/default scope and PMS help retains its English anchor. The production official API owns those fixed compatibility URLs plus `/official-suite/assets/*`.

The application/service/compatibility-ID and queue contracts live in the [official suite owner](../../apps/official-suite/README.md). Source ownership alone does not authorize activation, a second writer, data migration or deployment. The previous inactive/delegated-artifact candidates keep their original gates. Current verification is consolidated at final integration: affected source/compatibility tests, the two roots' type/build checks, architecture/ownership contracts and representative browser boundaries.
