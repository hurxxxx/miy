# Official app identity bridge

This core-owned contract connects a previously authenticated independent-app session to the existing `AuthContext` for official HTTP routes. It reuses the original user graph, current system roles, company/app admission and source resource ACL functions. It does not accept an app session as a platform login bearer, create a new login protocol, or activate the official service.

## Approval and current authority

`approve_binding` is an internal core operation. There is no app-facing endpoint, manifest permission or self-approval route. Official binding approval, revocation and delegated resolution require a real READ COMMITTED transaction. REPEATABLE READ/SERIALIZABLE snapshots and DBAPI AUTOCOMMIT are refused: refreshing an ORM object cannot refresh an old database snapshot, and autocommit cannot hold approval locks and audit writes together. These operations never upgrade isolation or commit implicitly. The common platform login/authentication policy is unchanged. The caller must hold a current, non-impersonated platform administrator session; authority is checked again after acquiring the installation lock so revocation during a lock wait denies the approval. Approval requires an enabled, ready installation with a runtime reference and an exactly reviewed generation, verified release and artifact. The release snapshot must have official ownership. The binding also records the verification ID, environment, origin, explicit logical app IDs and approving actor/session; approval and the existing platform audit record commit together.

The `official_app_bindings` table belongs to the core migration owner. Migration `official_auth_binding_20261006` follows `independent_delegation_20261006`; it creates no approvals and enables no services. One immutable record is allowed for each installation/generation. Scope changes or a revoked binding require a new reviewed deployment generation. `revoke_binding` locks the owned binding row, rechecks the current administrator after that wait, and records revocation with the existing audit mechanism. Neither operation commits on behalf of its core caller.

Each delegated request revalidates the opaque app session through the existing app identity service. It checks the source login session and user, installation admission and group membership, granted identity permission, current release verification, bound artifact/generation/environment/origin and logical app admission. A current administrator's source role is preserved, but administrator status does not bypass company app disablement or binding scope. Impersonation is rejected by the app-session contract. A detached or stale `AuthContext` is never itself evidence of a current approval privilege.

## Route scope and ACL

`packages/contracts/app-contracts.json` owns `official_app_ids`; the existing generator emits the same `OFFICIAL_APP_IDS` to TypeScript and Python. Both approval and request resolution reject scopes outside that official set, including otherwise valid platform app IDs. `RouterSpec.logical_app_id` is supplied by the core-owned official registry and checked against this canonical set by composition tests. The composition installs this scope before authentication, including nested routers. Caller headers, query parameters, body fields, app names and user/role declarations cannot select it. The official HTTP composition alone overrides `require_auth_context`; the platform and legacy dependencies remain unchanged. Handler `require_current_user`, application gates, resource/action ACL and AI approval logic continue to run normally.

The 12 launcher app scopes are covered. DM, notifications, personal widgets, calendar and announcements have no canonical app-admission scope in this bridge and are closed. Docs/Whiteboard WebSocket handlers are not delegated by this HTTP adapter. The product's inactive composition continues to reject all business HTTP/WS before these handlers execute. The adapter is exercised through isolated test-only router composition; removing the inactive gate is not a supported activation procedure.

`resolve_auth_context_from_session_id` is a core-only helper used **after** delegated credential authentication. A session ID is not a credential, and no endpoint accepts it as one. The helper and bridge issue only identity/admission reads: no `last_seen_at` update, transaction commit or audit insert. Legacy login authentication retains its existing last-seen behavior. This does not make every business GET read-only; the separate writer/side-effect contract still applies.

## Transition limits and evidence

The bridge currently reads existing core authority tables in the same PostgreSQL database. It is not a remote introspection protocol, a least-privilege service DB role, or a completed trust/process boundary. The official artifact remains inactive; no operational binding, second API/worker, routing cutover or live DB grant is created. Before activation, the [cutover owner](../../../../../../platform-redesign/OFFICIAL_API_CUTOVER.md) requires writer fencing, routing and worker ownership, remote/core authority separation, WS/content/search ACL parity, and role/runtime preflight.

`test_official_app_auth.py` uses migrated disposable PostgreSQL, verified build evidence, the real app-session exchange, existing Docs/PMS ACL functions and real HTTP handlers. It checks unchanged roles/source principal, SQL read-only identity resolution, binding audit, exact generation/artifact approval, ordinary bearer separation and current revocation across independent transactions. `test_official_auth_composition.py` checks server-owned scope ordering and forged scope/user/role input. `test_api_composition.py` preserves the inactive runtime and endpoint/OpenAPI contracts. These tests do not claim a live service cutover or remote protocol validation.

DM attachment persistence flushes its new source row before writing the object. The source trigger therefore holds the ownership SHARE lock through object `put` and DB commit/rollback; a concurrent drain CAS waits for that accepted transaction. Requests beginning after drain cannot write the object. After a confirmed PostgreSQL commit rejection and successful rollback, persistence attempts removal of only the newly uploaded object. Rollback releases SHARE before that compensation, so an accepted request's cleanup can finish after drain has completed. A slow existing synchronous upload can delay drain, so operational activation still requires admission/drain and storage deadline work. No live storage was used to verify this boundary.

Commit acknowledgement loss is not a confirmed rollback: a committed attachment may still reference the uploaded object. Cleanup is allowed only for a SQLAlchemy DBAPI error carrying a real psycopg error, a non-invalidated connection and one of the explicit server-rejection SQLSTATEs `23502`, `23503`, `23505`, `23514`, `23P01`, `40001` or `40P01`. All other outcomes—including `40003`, `08007`, connection/timeout/untyped failures and rollback failure—preserve the new object and return localized HTTP 500 `dm.attachment_save_unknown`, with no automatic retry. Errors do not expose the original SQL or connection cause. One subsequent SELECT cannot prove a delayed commit will never succeed, so there is no read-then-delete inference. The current composer makes one upload attempt per explicitly selected file and displays the error; it does not retry the failed upload automatically.

An unknown result may leave a committed, unsent attachment or an orphan object if no commit occurred. Neither this path nor failed known-rejection cleanup has a durable DM cleanup/reconciliation queue. Operator observation and an explicit retention/reconciliation policy remain necessary before service cutover; no destructive sweeper or automatic resend is introduced here. A table fence therefore does not establish complete object recovery or imply that all external I/O has stopped. The explicit unknown SQLSTATE names follow the [PostgreSQL error-code contract](https://www.postgresql.org/docs/18/errcodes-appendix.html).

DM realtime publication happens after DB commit. Rejected mutations must emit no event; a notification for an already committed mutation may finish after drain, and its current recipient/history ACL remains authoritative. This slice does not add a distributed publication outbox, move the shared realtime consumer or promise withdrawal of already accepted effects. DM is in the suite API/model inventory but is not a separate canonical launcher app in the current official 12-ID list; no delegated logical-app scope is invented here. The new source-only role still lacks identity/admission reads and common service authority and cannot run the whole DM or official service. `owner='official-suite'` remains unavailable.

### Full fixed source inventory and external-effect boundary

`official_source_writer_20261007`, following `official_dm_writer_20261007`, extends the fixed inventory from 19 to all **88** source tables declared by the suite ownership model inventory. The 69 additions are Bento (3), Community (4), Diagrams (1), Files (8), Mail (9), Meeting (8), remaining PMS/space sources (23), Recording (5), Video Chat (1), and Whiteboard (7). The shared mixin gives every source the same fixed `official.suite` CHECK/FK. PostgreSQL statement triggers reject INSERT/UPDATE/DELETE/COPY and TRUNCATE during drain, including zero-row statements. Source reads and original user/resource ACL do not gain or lose authority through this mixin.

The forward migration contains its own frozen 19+69 inventory and does not import mutable runtime lists. Under the ownership lock it requires an actual READ COMMITTED transaction and the exact homogeneous old guard inventory. Existing cooperative legacy execution stays compatible. An already hardened DB must first be draining; all new sources receive that same guard, without any role grant. Only after all 88 guards exist may an explicit core controller prepare a new LOGIN/generation with the complete inventory, install/verify the hardened guard, retire the prior role and perform exact CAS. Replaying an older principal never grants the new 69 sources. Active hardened/malformed/disabled/mixed guards fail closed. Hardened downgrade still requires explicit retirement; code rollback requires a fresh identity/generation rather than a schema downgrade. All earlier migrations remain unchanged.

`source_guard.lock_source_writer` performs a zero-row UPDATE against an allowlisted source after its original ACL. The real statement trigger acquires the same ownership/principal SHARE locks as source DML; they last until the caller commits or rolls back. The helper accepts neither caller SQL nor a runtime identity override, and refuses AUTOCOMMIT and stale-snapshot isolation. It is used before PMS/Meeting attachment uploads, Recording spool writes/imports, Diagrams storage writes, and new Video Chat token signing. Recording completion reacquires it after **each** intermediate commit, before assembly and object upload; revocation of existing Recording jobs also begins behind the guard. A fenced or failed completion leaves its original spool and does not claim successful promotion. Earlier assembling/uploading status commits remain durable and still need explicit recovery.

External objects are not transactional PostgreSQL rows. PMS/Meeting attachment deletion, Recording staging discard, Meeting deletion and stale spool cleanup delete original bytes only after an acknowledged metadata commit. Diagrams updates write fresh versioned keys instead of overwriting the current source/preview; obsolete keys are retired only after acknowledged pointer commit. Commit rejection or an unknown result therefore cannot delete the old referenced bytes. Unknown results may retain unreferenced new keys or spools; there is no new destructive sweeper or automatic retry.

Normal Files upload shares the narrow confirmed PostgreSQL rejection classifier with DM. Only those explicit non-invalidated DBAPI rejections plus successful rollback permit immediate cleanup of a newly uploaded key. Other commit errors return the localized `files.metadata_save_unknown` HTTP 500: the result is unknown, bytes were preserved and callers should inspect before retrying. Existing frontend upload has no automatic retry. Files external-source lifecycle separately observes the root Connection's COMMIT attempt and its Session acknowledgement. Missing acknowledgement preserves bytes even if a later Session rollback/close occurs. A savepoint release cannot establish root success: released or uncertain-savepoint keys move to the parent; explicit pre-COMMIT outer/savepoint rollback still compensates its own new keys. Its event hooks do not classify commit exceptions, so an unacknowledged root attempt is conservatively preserved even if the server in fact rejected it. Durable Files cleanup jobs for acknowledged replacements remain unchanged.

A source lock is **not** an external-effects or service-readiness claim. Storage may remain blocked synchronously while its transaction holds SHARE, and accepted post-commit cleanup/realtime events may finish after drain. Recording pipeline publication, Mail committed send/sync attempts, Files cleanup workers, shared queue/Beat ownership, already issued LiveKit tokens, browser/WS routing and exact per-runtime credentials remain separate cutover work. Source-only roles lack common identity/ACL/outbox authority; 88 guarded tables do not make an official API or worker runnable. No activation switch, deployment, operational role/grant or object-store change is included.

`writer_roles.py` is a separate, explicit core preparation boundary for the 88 source tables in `writer_contracts.py`. Migration `official_writer_roles_20261006` follows `official_writer_fence_20261006`. It adds immutable principal bindings and a private `SECURITY DEFINER` trigger function; it does **not** replace the existing cooperative GUC guard, create roles, issue credentials, change running service grants or enable an official writer. The current shared-role service still uses the previous guard.

The caller supplies a pre-provisioned, lower-case PostgreSQL LOGIN role for each artifact/generation and a separate NOLOGIN function owner. Both must be `NOINHERIT`, have no privileged role attributes, no incoming/outgoing membership, and no unexpected database/schema/object ownership. Preparation checks effective privileges, including PUBLIC, column-only grants, sequence privileges, executable security-definer functions, grant options and explicit parameter privileges such as `SET session_replication_role`. Object checks cover the current database; cluster role attributes/membership and database ownership are checked globally. This is not a complete audit of grants inside other databases. Unexpected authority is refused without changing existing grants. Creating credentials, validating them against a deployment and distributing them remain operator/runtime work; these functions never accept a password. No HTTP endpoint, CLI, startup hook or environment switch exposes this preparation.

The three core functions use an exact expected ownership snapshot and the existing live, non-impersonated administrator resolver. They acquire the ownership row before rechecking administrator authority. Their changes and audit records belong to the caller's clean READ COMMITTED transaction; they never commit it. Actual DBAPI AUTOCOMMIT is refused even though PostgreSQL reports its default isolation as READ COMMITTED. REPEATABLE READ/SERIALIZABLE snapshots are refused because refreshing ORM objects would not observe an administrator revocation committed during a lock wait.

1. `prepare_principal` binds the role's OID **and name** once to `official.suite`, legacy owner, generation and a non-null SHA-256 artifact digest. It grants public-schema usage and SELECT/INSERT/UPDATE/DELETE on only the 88 source tables, then rechecks current administrator authority after the grant operations. This is a core assertion of the artifact association, not a verified deployment or image attestation. Before creating a new binding or granting privileges, preparation checks the complete current source trigger inventory under the ownership lock: exact public function, homogeneous legacy or role guards, enabled events and the single fixed suite argument. A newer binary therefore refuses to grant an unfenced source against an older schema. Repeating the exact live binding is allowed without new grants or audit, including its historical source inventory; a different identity, renamed/recreated role or revoked binding is refused. A new generation/artifact requires a new role and binding.
2. `install_role_guard` requires the exact **draining** state. It checks the complete 88-table trigger inventory and the private function's fixed security/search-path contract. In one savepoint, it assigns the function to the NOLOGIN owner, grants that owner only the SELECT/UPDATE needed for `FOR SHARE` on ownership/principal rows, removes temporary schema CREATE, and replaces the 88 triggers. It rechecks current administrator authority after DDL lock waits. Revocation while waiting rolls back the new triggers, function ownership, grants and audit. The function is not executable by PUBLIC. Schema/table owners and the privileged core controller remain trusted and are not protected against by this boundary.
3. `revoke_principal` only sets an irreversible revocation timestamp under the same lock order. The database immutability trigger rejects identity edits, deletion and un-revocation. Existing source transactions finish before controller/revocation changes; later statements from an already-open revoked login fail. Code rollback uses a fresh role and monotonically newer ownership generation, never remaps an old principal or automatically downgrades schema.

Once explicitly installed, the hardened trigger uses **`session_user`**, not `current_user` or the app-controlled GUC. It joins the current PostgreSQL role OID/name to the immutable mapping, then compares exact owner/generation/artifact and active state under shared row locks. A new role with a reused name, stale live connection, forged transaction setting or `SET ROLE` cannot adopt a new identity. The function uses qualified tables and `search_path=pg_catalog,pg_temp`; temporary tables cannot shadow its authority. The runtime role cannot read or directly modify ownership, principal, transition or audit tables, change triggers, grant itself another identity or TRUNCATE sources. The same SQLSTATE/error identifiers preserve the existing localized HTTP 503 mapping. PostgreSQL's security-definer/search-path and session-identity rules are the underlying mechanism. ([CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html), [session identity](https://www.postgresql.org/docs/current/functions-info.html))

This restricted legacy principal cannot run the whole legacy API or official service: authentication/admission reads, original resource ACL, platform outbox/audit/projection writes, worker/queue ownership and post-commit external effects still need their explicit shared-boundary design. Source DML grants are service authority, not per-user row authorization; existing server ACL must still run. While the cooperative guard remains installed, preparing a role does not make that guard authenticate GUC values. Do not hand a prepared credential to an app or treat preparation as readiness. An actual switch still requires prior source drain, reviewed runtime/credential and worker/routing coverage, concrete approval and later exact CAS to reopen the permitted legacy generation. `owner='official-suite'` remains unconditionally unavailable.

The roles and grants are currently exercised only in an owned disposable PostgreSQL cluster. `test_official_writer_roles.py` uses fresh actual LOGIN connections, full Alembic migrations and the existing administrator/session resolver. It covers ORM/migration nullability and CHECK parity, table and column privileges, GUC/role/replication-setting forgery, temp shadowing, immutable/revoked identities, retained old sessions, real record/COPY writes and rollback, concurrent source/controller locks, and administrator revocation during both row and DDL waits. Downgrade is refused while the hardened function is attached; ordinary migration rollback before activation preserves the legacy guard. No operational role, credential, trigger or service has been changed.
