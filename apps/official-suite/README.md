# Official suite composition

This project owns the first separate UI composition/build target for the official business apps. `OFFICIAL_APP_IDS` in the shared app contract owns membership and ordering. The suite-owned [official UI source library](../../packages/official-suite-web/README.md) owns the twelve app manifests, help composition and Diagrams/Bento/Mail/Whiteboard/Community/Docs/Recording/Meeting/Planner/PMS implementations, independent of either UI root. The temporary `apps/web/src/app/shell/official-app-modules.ts` adapter directly consumes all twelve official module entries; both UI roots use the same contract-owned membership/order. `ownership.json` records the UI metadata, API, model and worker source ownership for this transition. It is checked against the current tree and does not activate services or SQL grants.

From the repository root, use the existing workspace dependencies:

```bash
pnpm nx ownership official-suite
pnpm nx test official-suite
pnpm nx typecheck official-suite
pnpm nx build official-suite
```

The build output is `dist/apps/official-suite`, separate from `dist/apps/web`. `pnpm nx dev official-suite` starts the local UI on port 4201 with the existing `MIY_WEB_API_PROXY_TARGET` development API connection; it does not start another API/worker/migrator. The suite root includes only its owned app registrations and preserves their `/apps/*` deep links and current admission checks. The main portal retains its current registration order and routes.

`OfficialSuiteRoot` and the legacy `AppRoot` select `OFFICIAL_HELP_GUIDES` directly from `@miy/official-suite-web`. Both pass the selected `HelpGuide` metadata to the shared help modal and use `createDefaultHelpRoutes` for `/help`, `/help/pms` and the existing AI guide routes. The shared help renderer imports no business app and has no implicit app guide; the suite leaf registration owns the unchanged document path, translation keys and English `#english` section resolver. `AppModuleManifest` and `HelpGuide` contracts belong to `core-web`, with compatibility re-exports in web. Help metadata is presentation content, not app admission or resource access authority.

This is stage zero of the [official app transition](../../platform-redesign/OFFICIAL_APPS.md). Pure business manifests, the Diagrams view/API/model/draw.io implementation, the Bento view/API/protocol/route-builders/background-work implementation and the Mail view/API/workflow/sanitizer implementation have moved into the suite-owned library; their old web paths are compatibility re-exports. The shared browser AuthContext, HTTP client and time implementation are owned by [platform-web](../../packages/platform-web/README.md), while the existing AuthProvider lifecycle and i18next initialization remain in the platform root. Diagrams routes/sidebar and Bento/Mail routes/module composition also belong to the suite; their old paths are thin exports. Other views and API clients still enter through the explicit legacy app-module list. The shared UI shell, auth/bootstrap client, translations, styles/public assets and Vite configuration remain explicit legacy bridges. Suite TypeScript uses the named `@miy/web-official-suite-bridge` entry for these remaining implementations; the suite-only ESLint exception permits that exact entry, while other app imports and cycles remain checked. Web imports the suite-owned source library, never the suite application project. Neither the official UI source library, platform-web nor shared core-web contracts may import either app root. Remove the bridge and its exception when the remaining shared UI and business source become owned libraries. The new target has a real separate entry and artifact directory, but is **not an independently releasable full service**. Its API/worker/DB writer and migration owner remain the existing single deployment. No production routing, official app-ID takeover, source ACL delegation or queue consumer is switched by these files.

DM/Calendar views currently enter through legacy home widgets; notifications, realtime chrome and cross-app personal widgets still need their own public summary/ACL contracts. They are recorded in the ownership survey and are not imported as a hidden second legacy root. The new UI currently omits those global widgets and realtime chrome while preserving the selected app routes. App code and resource APIs retain their existing authorization checks. The suite must not be embedded using a platform bearer token or enabled as a second data writer to work around these remaining contracts.

Planner now has a complete source owner in `packages/official-suite-web/src/planner`: calendar/timeline, floating widget, routes/sidebar/module and Meeting/PMS aggregation join the existing narrow event editor/API. The official `calendar` source owns the fixed business event DTO/API, FullCalendar wrapper/adapter and theme CSS shared with PMS; roots load the same CSS once. Generic holiday lookup, fallback colors and floating event protocol belong to platform-web with same-object compatibility entries. Module, API, date policy and root dock/provider lifetimes are preserved. This source move activates no writer and modifies no calendar data.

Video Chat also records a partial source owner: `packages/official-suite-web/src/video-chat` owns the lobby and existing API module, while the actual room/LiveKit/media runtime remains in web and consumes the same API through compatibility exports. This moves room listing/creation UI ownership without activating another service, changing admission or moving device/media/session-token lifecycle. Synthetic lobby tests and both-root browser fixtures use no real room or media connection.

Meeting now has a complete source owner in `packages/official-suite-web/src/meeting`: all forms/list/detail/availability/insights/recording UI, routes/sidebar/module and its Korean/English messages. Its original narrow API/picker entry remains unchanged; the full public union and the module's existing lazy creation/detail wrappers are separate public entries, so Planner uses the same components without pulling screens into API consumers. Former paths retain the same objects. Common form composition, remote-user search and existing AI/conversation/Hermes HTTP adapters are actual platform-web source; Chatbot UI, personal widgets and root initialization are not moved. This ownership change enables no writer/service, device request or extra session lifecycle. Files and Video Chat now also have complete source owners.

Before a runtime release, finish authenticated suite delegation, official-ID ownership migration, source/retrieval/outbox/worker boundaries and current ACL parity. Existing Alembic remains the only platform migration runner; data migrations and writer cutover need their own reviewed implementation and validation. The new UI artifact is not added to the current production compose/release contract until those steps are ready.

The [API composition artifact](api/README.md) adds a separate official wheel and platform/official route ownership, while keeping both split profiles inactive. `pnpm nx api-contract official-suite` checks their endpoint/health/activation contracts; `pnpm nx api-build official-suite` builds the official and compatibility API wheels. The [cutover owner](../../platform-redesign/OFFICIAL_API_CUTOVER.md) records the concrete shared writes and next writer/queue/routing steps. UI, API artifact, worker ownership and running service are separate completion states.

The complete PMS UI now has an official source owner: `packages/official-suite-web/src/pms` contains the browser API, filters, UI role hints, reorder adapters, pickers, all task/space/list views and controllers, sidebar and floating widget. Its narrow public API remains unchanged; `/pms/module` supplies the full existing composition. The legacy public/leaf exports preserve runtime identity while Docs, Home, Meeting, Planner and Recording consume its public entry. The shared pure ordering implementation belongs to `platform-web`; no app implementation or root initializer is imported back into that library. The existing common shell-navigation helper belongs to platform-web, while each root keeps its single auth/admission/i18next initialization. The canonical PMS help HTML is suite-owned and keeps its fixed URL and English anchor through the same two-asset Vite lifecycle as the Recording worker. This extraction does not create a separate PMS service or release and does not activate a writer.

Whiteboard now has a complete source owner in `packages/official-suite-web/src/whiteboard`: its API, scene/collaboration implementation, editor/hub/sharing/context panels, library assets and route/sidebar/module composition. Existing web entries export the same owned objects. Meeting and PMS use its public lazy API. The shared realtime Provider/runtime, company-directory and user-picker source now belong to platform-web; the portal keeps its single live Provider mount, while the stage-zero suite now supplies the same Context through one offline Provider (`token=null`), with no platform realtime connection. Auth/i18next initialization remains in each root. Two official modules remain explicit transition entries. This source move changes no backend writer, admission policy, WebSocket endpoint or service activation.

### Community source ownership

Community is now a complete suite-owned UI module under `packages/official-suite-web/src/community`, including routes/sidebar, browser API/cache, screen, Markdown editor/CSS and its Korean/English catalog. The root registry consumes its public module; admin Community settings consume public editor/event entries. Former web paths are same-object compatibility exports. Common auth HTTP/role-display helpers, media upload/URL session and UserDateTime belong to platform-web, together with locale/session helpers and common/auth messages. Root AuthProvider, the single i18next initialization and catalog composition retain their existing lifecycle. No bearer, admission, server write, registration, service or deployment behavior changes.

Ten official modules now own their complete source/module composition (Diagrams, Bento, Mail, Whiteboard, Community, Docs, Recording, Meeting, Planner and PMS); two remain explicit transition modules. Community API/URL/manifest tests move with source, while the existing root Korean screen test verifies host composition. Structural checks cover source-body and catalog-value parity, the same error/function/Context objects, lazy loading and forbidden reverse imports. Separate official packaging, remaining root composition and service activation are still incomplete.

Docs now has its complete UI source owner in `packages/official-suite-web/src/docs`, including API, hub/sidebar/routes, picker/viewer, block and HTML surfaces, sharing/publication controls and Korean/English messages. The root and nineteen cross-app public consumers use the suite entries; previous paths preserve object identity through compatibility exports. The shared platform primitives and single root auth/i18next/realtime initialization retain their existing lifecycle. Two official modules remain explicit transition entries. This is an ownership move only; it changes no server permissions, API response, document-save behavior, service activation or independent release boundary.

Recording now has its complete source owner in `packages/official-suite-web/src/recording`, including recorder/recovery/storage, browser API, list/detail/public views, route/sidebar/module and its Korean/English messages. Shared app-link helpers and request concurrency belong to platform-web; previous imports preserve object identity. Its fixed Service Worker is owned at `packages/official-suite-web/public/recording-sync-sw.js` and served/emitted by the fixed two-asset Vite plugin inherited from the common web config. Existing registration URL, default scope, bytes, recorder/device/session/storage lifecycle and network behavior remain unchanged. Structural checks use synthetic transports and owned Vite fixtures; no microphone, real recording or stored user data is accessed. Two modules still enter through explicit transition imports, and the root bridge/service activation remain incomplete.

Files routes/sidebar/chat composition now uses its official owner and the actual common platform Chatbot public experience. Video Chat module/routes/room join the existing suite lobby/API, with root initialization and original lazy SDK/style imports retained. Current login/room changes retire room state and late responses; the pinned SDK disconnects its old connection. These source changes and local tests do not perform runtime/provider/service cutover or app-wide media acceptance.
