# MIY 플랫폼과 Workbench 재설계 계획

계획 기준일은 2026-10-06이다. 이 문서는 대화에서 확정한 목표 설계를 기록한다. 현재 구현 여부와 실행 권한은 [STATUS.md](STATUS.md), 작업별 진행은 [WORK_ITEMS.md](WORK_ITEMS.md)에서 확인한다.

웹 재검토의 `R-01`~`R-08`을 사용자 수정 요청에 따라 목표 설계에 반영했다. 근거와 반영 위치는 [REVIEW.md](REVIEW.md)에 연결한다. 설계 반영은 제품 구현이나 활성 지침 변경의 완료를 의미하지 않는다.

## 1. 목표와 범위

공통 플랫폼, 공식 앱, 현업 제작 앱, Workbench의 개발·실행·배포 경계를 분리한다. 신규 앱은 지원하는 계약을 만족하면 포털·Workbench의 앱별 코드 수정 없이 등록·실행·개발·배포할 수 있어야 한다.

### 네 영역의 책임

| 영역             | 개발 책임       | 주요 역할                                                                  | 배포 단위             |
| ---------------- | --------------- | -------------------------------------------------------------------------- | --------------------- |
| 공통 플랫폼·포털 | 코어 개발자     | 인증, 조직·사용자, 앱 등록·입장 권한, 런처, 공통 API·SDK, 감사, AI Gateway | 플랫폼                |
| 공식 앱          | 코어 개발자     | 메신저·채팅·PMS·파일·회의·스케줄러 등의 업무 기능                          | 초기에는 공식 앱 묶음 |
| 현업 제작 앱     | 앱 담당자와 LLM | 개별 업무 화면·규칙·데이터·테스트                                          | 앱별 독립 배포        |
| MIY Workbench    | 코어 개발자     | Codex 작업, 하네스·템플릿 활용, 개발 환경과 운영 상태 관리                 | 독립 Workbench 서비스 |

현업 제작 앱은 개발 주체를 뜻한다. 사용 대상은 전사·팀·특정 사용자로 별도 설정한다. 공식 앱에서도 개인 콘텐츠의 기존 권한을 유지하며, 개발 소유자 구분을 데이터 공개 범위로 해석하지 않는다.

공통 플랫폼·공식 앱·Workbench는 코어가 관리하는 현재 저장소에서 시작하되 프로젝트·빌드·서비스·릴리스 경로를 분리한다. 현업 제작 앱은 앱별 저장소를 기본으로 한다. 같은 서버 사용 여부와 코드·데이터·배포 경계는 구분한다.

### 이번 범위

2026-10-10 사용자 지시로 **구조를 완성하는 데 반드시 필요한 작업만 수행**한다. 아래 항목이 이번 완료 기준이며 이후 절의 확장 설계 전체를 구현할 의무로 취급하지 않는다.

- 하나의 앱 등록 원본을 포털·Workbench가 읽어 발견·선택·소스 연결하고 목록 차이·오류를 설명한다.
- 공통 플랫폼·공식 앱 묶음·개인 앱·Workbench의 소스·빌드·실행·릴리스 경계를 완성한다. 개인 앱 변경은 플랫폼/공식 앱 전체 재빌드·재시작을 요구하지 않는다.
- 기존 서버 인증·실행 주체·앱/리소스 ACL·데이터 소유를 유지하고 분리 과정의 실제 권한 우회·유실·중복 쓰기를 방지한다. 같은 PostgreSQL 서버나 공통 저장 서비스를 재사용할 수 있다.
- 개인 앱의 최소 manifest·SDK·격리 개발·미리보기·독립 배포·복구를 기존 단일 사용자 Codex Task에 연결한다. 기본 선택·실행·중단·재개·상태 확인과 필수 명령 템플릿만 완성한다.
- 대표 UI 앱과 DB·권한 앱으로 등록→개발→미리보기→배포→복구, 권한·데이터 보존을 통합 확인한다. 필수 릴리스 계약과 설치/운영 소유 문서를 맞춘다.
- 이번 구조를 기존 방식으로 되돌리는 실제 지침 충돌만 해소하고 중요한 계약을 유지한다. 전역 하네스 정리나 반복 품질 평가를 완료 선행 조건으로 추가하지 않는다.

### 후속 범위

고급 Workbench UX·모니터링·템플릿, 반복 자연어/모델 평가, 병행 부하 측정, 복잡한 저장 프로토콜 확장, 추가 서비스 세분화·SDK 확장은 [후속 고도화 작업](FOLLOW_UP_ENHANCEMENTS.md)으로 분리한다. 모두 별도 사용자 지시 전까지 `deferred`이며 이번 구조 완료를 막지 않는다. 앱별 상세 개선·테스트는 [APP_ISSUES.md](APP_ISSUES.md)가 계속 소유한다.

다중 사용자 Workbench의 로그인·사용자별 권한, 개발자 사이의 작업·자격증명 격리, 공유 Workbench용 PostgreSQL 전환, 여러 개발자의 자원·계정 배정은 이번 구현에서 제외한다. 기존 한 사용자의 여러 Task 기능은 유지하되 새 동시 실행 수용량 목표·성능 고도화는 후속으로 미룬다.

MIY 업무 앱의 기존 다중 사용자 기능과 사용 권한은 유지한다. Workbench 다중 사용자를 미룬다는 이유로 플랫폼의 사용자 인증과 데이터 권한을 단순화하지 않는다.

공식 앱을 각각 별도 서비스로 세분화하는 것은 필요가 확인될 때 진행한다. 이번에는 공식 앱 묶음을 플랫폼과 분리하는 데 집중한다.

### 구조 완성 우선과 앱별 후속 작업

2026-10-07 사용자 지시에 따라 이번 구현은 **네 영역의 구조를 완성하는 데 필요한 변경과 검증**에 집중한다. 아래 기준은 이후 작업 선택과 완료 판정에 적용한다. 이미 수행한 수정·검증은 보존하고, 과거의 넓은 검사 범위를 매번 반복할 의무로 삼지 않는다.

| 구분                            | 이번 처리                                                              | 판단 근거                                                                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 구조 완성에 필수                | 재개 후 현재 구현에서 수정·검증                                        | 코드 소유와 공통 계약, 의존성·초기화, 별도 빌드·실행·배포·복구, 동적 앱 등록, native Codex 연결 등 목표 구조가 성립하는 데 필요                           |
| 구조 이행 중 확인한 치명적 문제 | 재개 후 현재 범위에서 바로 수정하고 영향 경계를 검증                   | 권한 우회·자격증명 노출·데이터 유실/손상·중복 쓰기·다른 앱/사용자 영향·핵심 실행 불능 등 구체적인 실패나 코드 근거가 있음. 기존 결함이어도 동일 기준 적용 |
| 앱별 비필수 개선·상세 기능 검증 | [앱별 이슈 대장](APP_ISSUES.md)에만 기록하고 별도 사용자 지시까지 보류 | 업무 규칙 확장, 화면 다듬기, 비치명적 사용성 문제, 앱 전체 업무 시나리오·세부 경우의 전수 검사 등 구조 완성을 막지 않음                                   |

구조 이전 때문에 생긴 호환·계약 위반은 현재 범위에서 바로 고친다. 앱 화면이나 데이터 경로의 수정도 구조상 필요하면 진행한다. 반대로 앱 파일을 옮겼다는 이유만으로 그 앱의 모든 기존 기능 개선·테스트를 추가하지 않는다. 이슈를 기록하려고 상세 조사·재현 환경·새 테스트·수정을 자동으로 시작하지 않으며, 분류에 필요한 근거가 부족하면 미확인으로 남긴다. 치명적 영향 가능성이 구체적으로 드러난 경우에는 그 경계를 판별할 최소 확인을 현재 작업에서 수행한다.

후속 이슈는 구조 작업의 의존성이나 인수 조건으로 자동 추가하지 않는다. 구조 작업이 끝나거나 사용자가 일반적으로 “계속”이라고 해도 후속 이슈를 자동 실행하지 않는다. 해당 앱/이슈의 조사·개선·상세 검증을 별도로 지시받았을 때 착수한다. 이후 근거로 구조 필수 또는 치명적 문제로 판단이 바뀌면 사유를 기록하고 현재 구조 작업에 연결한다. 이 기준은 필수 검증·CI·권한·릴리스 경계를 면제하지 않으며 운영 변경 권한을 확대하지 않는다.

신규 journal/checkpoint/native adapter·Files 전체 publication 설계는 자동 필수가 아니다. 기존 안전한 트랜잭션·저장 서비스·소유 경계 재사용을 우선하며, 실제 분리 장애나 치명적 결함의 근거가 있는 최소 부분만 현재 작업으로 연결한다. [후속 문서의 조건부 기준](FOLLOW_UP_ENHANCEMENTS.md#조건부-항목을-다루는-기준)을 따른다. 미게시 후보와 과거 검증 자료는 보존하고 미채택 후보를 활성화하지 않는다.

### 전체 구조를 통합한 뒤 검증하기

2026-10-10 사용자 추가 요청으로 기능 묶음별 검증보다 더 크게 모은다. **이번 재설계의 남은 구조 구현·통합을 먼저 진행하고, 하나의 최종 통합 검증에 이어 필수 리뷰·CI와 승인된 반영 확인까지 진행**한다. Workbench·공통 저장/권한·공식 앱·개인 앱·최소 하네스의 구현 경로를 나누되 경로별 전체 검사·게시·배포를 반복하지 않는다. CI가 담당하는 전체 검사를 로컬에서 미리 중복 실행하지 않는다. 구현 중에는 진행을 막는 오류와 구체적인 치명적 경계의 최소 확인만 수행한다. 실패 수정 후에는 해당 경계부터 재검증하고, 새 변경·실패·필수 계약이 요구할 때만 넓힌다.

검증 템플릿은 기존 진입점을 한 요청에서 준비→필요 검사→정리→결과 보고로 연결한다. 자연어 대표 사례도 전체 흐름에 포함해 기본 1회 수행한다. 상세 범위·반복·릴리스 선택은 [검증 일괄 수행 원칙](VALIDATION.md#2026-10-10-검증-일괄-수행-원칙)이 소유한다. 필수 권한·데이터·실행 경계와 릴리스 게이트는 유지한다. 범위 점검 후 사용자의 재개 지시로 필수 구현을 진행 중이며, 구현 후보와 실제 검증·반영 완료를 구분한다.

## 2. 현재 문제와 선택 근거

앞선 읽기 전용 조사에서 별도 `open-work-hub` 프로젝트의 등록 앱 25개 중 Workbench에 18개가 표시되는 것을 확인했다. 선택 항목인 `management`가 없으면 제외하는 구현 때문에 지원자 서류평가, 채용 대상자 지원서 서류 평가, ScaleBridge 등이 누락됐다. 이 수치는 당시 원격 프로젝트의 관측이며 현재 로컬 저장소의 앱 수나 재검증된 운영 상태가 아니다.

구현 착수 당시 [Workbench 카탈로그](../apps/codex-console-api/src/codex_console/workbench.py)에도 해당 제외 조건이 있었다. 현재 수정 상태와 검증은 [STATUS.md](STATUS.md)와 [VALIDATION.md](VALIDATION.md)가 소유한다. 기존 [앱 계약](../packages/contracts/app-contracts.json), [웹 모듈 조립](../apps/web/src/app/shell/app-module-manifests.ts), [API 조립](../apps/api/src/miy_api/api_registry.py)은 내장 앱 중심이다. 카탈로그 항목을 추가하는 것만으로 독립 실행·배포가 되지는 않는다.

| 검토한 방식                     | 판단                                                               |
| ------------------------------- | ------------------------------------------------------------------ |
| 현재 구조에서 카탈로그만 보강   | 누락은 해결하지만 코드·실행·배포 결합은 남음                       |
| 개발 환경마다 MIY 전체 복제     | 기존 구조 재현은 쉽지만 반복 자원 비용과 배포 결합을 해결하지 못함 |
| 공통 플랫폼과 독립 앱 실행 환경 | 앱별 개발·미리보기·배포를 지원하는 목표 구조로 채택                |

확장성은 지원하는 계약에 맞는 앱을 추가하는 능력으로 정의한다. 알려지지 않은 모든 기술을 자동 수용한다고 가정하지 않는다. 새 실행 유형이 필요하면 버전 있는 공통 계약을 확장하며 특정 앱 ID의 예외를 추가하지 않는다.

## 3. 앱 등록과 실행 계약

### 정의와 실제 설치 상태

| 계약                | 소유하는 정보                                                                |
| ------------------- | ---------------------------------------------------------------------------- |
| `AppDefinition`     | 안정적인 앱 ID, 이름·번역·아이콘, 개발 소유자, 소스 위치, 지원 기능          |
| `AppRelease`        | 소스 버전, 변경 불가능한 산출물, SDK 호환성, 검증·마이그레이션 정보          |
| `AppInstallation`   | 설치 환경, 실행 주소, 적용 릴리스, 사용 대상, 승인 권한, 실행 상태           |
| 개발 환경 연결 정보 | 앱, 저장소·브랜치, 작업 디렉터리, 실행 환경, 미리보기와 기존 Codex 작업 연결 |

앱 저장소의 버전 있는 manifest를 정의의 원본으로 삼는다. 등록 서비스가 검증해 플랫폼 저장소에 반영하고 설치·사용 대상·권한·실행 상태는 서버가 관리한다. 기존 계약 파일은 전환용 어댑터로 읽는다. 원본 정의와 서버 투영을 각각 수동 편집하는 이중 등록 구조를 만들지 않는다.

manifest는 UI·API·필요한 worker·예약 작업, 요청 권한, 빌드·테스트·마이그레이션을 선언한다. 실행 주소와 자격증명은 실행·배포 서비스가 관리한다. 선언된 요청 권한이 곧 부여된 권한은 아니다.

- 포털과 Workbench는 같은 정의의 이름·번역·아이콘을 사용한다.
- Workbench는 조회 권한이 있는 앱 중 관리 정보가 부족한 앱도 표시하고 개발 설정 필요 상태를 제공한다. 앱 발견, 설치·사용 가능 여부, 개발 소스 연결, 미리보기 준비, 배포 가능 여부를 별도 상태로 표시하며 제한 이유를 설명한다. 관리 기능의 부재를 앱 부재로 처리하거나 권한 없는 앱 정보를 노출하지 않는다.
- 포털은 설치 상태와 기존 앱 사용 권한을 적용한다. 두 화면의 목적에 따른 목록 차이는 설명 가능해야 한다.
- 소스·등록·실행 상태가 어긋나면 원인을 표시하고, 확인 실패를 빈 목록이나 정상 상태로 바꾸지 않는다.
- 전체 목록을 조회할 수 있게 하며 고정된 200개 제한이나 첫 페이지에 의존하지 않는다.
- 신규 앱의 필수 절차에서 포털의 앱별 정적 import와 공통 API 서버의 앱별 router 등록을 제거한다.

manifest·SDK·공통 API는 버전과 호환 범위, 폐기 예고, 소비자 검증을 함께 관리한다. 지원되지 않는 버전은 명시적인 호환 오류로 처리한다. 정의의 검증·동기화 실패는 마지막으로 검증한 정의와 실제 설치 상태를 구분해 표시하며, manifest 오류·삭제를 운영 설치 제거로 자동 변환하지 않는다. 설치 제거는 별도 권한과 명시된 작업 범위로 수행한다. 같은 앱의 개발·운영 설치를 구분하고 기존 소비자는 명시한 호환 기간 동안 검증한다.

### 포털 임베딩과 독립 실행

포털은 탐색·런처·공통 화면 틀을 담당하고 업무 코드는 앱 실행 환경에서 실행한다. 신규 현업 앱은 별도 origin의 iframe으로 포털에 연결하며 독립 주소에서도 실행할 수 있게 한다. 기존 내장 앱은 이전 기간 동안 기존 경로로 공존한다.

공통 SDK는 테마·언어·탐색·파일 선택·공통 API 연결을 제공한다. 현재 기술을 활용한 권장 웹·API 템플릿을 제공하되 실행 계약을 특정 UI 프레임워크에 종속시키지 않는다. 앱 이동·새로고침·직접 링크에서도 기존 앱 ID와 경로 의미를 보존한다.

### 인증과 데이터

현재 MIY 인증을 유지하면서 사용자·앱·설치 환경에 한정된 앱 세션 교환 기능을 추가한다. 이미 OIDC 기반 인증이 구현되어 있다고 가정하지 않는다.

- 포털 로그인 토큰을 iframe에 전달하지 않는다. 임베딩과 독립 실행은 같은 앱 세션 계약을 사용한다.
- 앱 세션은 사용자·앱·설치·환경·대상 API와 허용 동작에 한정한다. 발급·만료·갱신·철회, 교환 요청의 재사용 방지와 실패 처리를 계약에 포함한다. 앱 세션·교환 자격증명을 URL·로그에 노출하지 않는다.
- iframe 통신은 정확한 `targetOrigin`, 수신 `origin`·`source`, 버전 있는 메시지 형식을 검증한다. iframe 교체·탐색 시 통신 상대를 다시 확인한다. 포털의 허용 프레임과 앱의 허용 호스트 정책을 함께 적용한다.
- 앱 입장 권한과 원본 서비스의 데이터 권한은 서버에서 확인한다.
- 권한 철회는 후속 API 요청에도 적용한다. 임베딩과 독립 주소의 로그인 시작·만료·재개를 정의하고, 제3자 쿠키 제한이 있는 브라우저에서 실제 배치 도메인으로 검증한다. 서로 다른 origin과 서로 다른 site를 같은 것으로 가정하지 않는다.
- 앱 내부 업무 데이터의 권한도 공통 SDK와 앱별 검증 대상으로 삼는다. 카탈로그 등록이나 LLM 판단이 데이터 접근 권한을 대신하지 않는다.
- 앱·환경별 DB 계정과 객체 저장소 영역을 분리한다. 같은 PostgreSQL 서버를 사용할 수 있지만 다른 앱이나 코어 DB의 직접 접근 권한을 주지 않는다.
- 개발에는 독립된 테스트 데이터를 사용한다. 운영 배포에는 코드와 마이그레이션을 승격하며 개발 데이터는 옮기지 않는다.
- 운영 앱은 자신의 운영 DB와 승인된 운영 API를 사용한다. 개발 세션에는 운영 DB 자격증명을 제공하지 않는다.

파일 앱의 업무 기능은 공식 앱 영역, 공통 객체 저장소는 플랫폼 영역으로 구분하는 식으로 업무 기능과 기반 기능의 소유자를 정한다. 공식 앱의 기존 데이터 권한은 경계 이동과 별도로 보존한다.

직접 링크·새로고침·앱 내부 이동·키보드 포커스까지 브라우저에서 확인한다. iframe 격리가 앱 인증·API 권한을 대체하지 않으며 OIDC 전환을 선행 조건으로 추가하지 않는다.

## 4. 개발 환경과 배포

이번에는 한 사용자가 여러 앱을 병행할 수 있도록 앱·작업 브랜치별 개발 환경을 제공한다. 공통 개발 플랫폼 하나에 작업별 코드·앱 프로세스·네트워크·데이터·미리보기 주소를 연결한다.

- 로컬 PC와 개발 서버에서 같은 개발 컨테이너 템플릿과 앱 계약을 사용한다.
- 로컬에서는 독립 테스트 데이터와 개발용 플랫폼 연결을 사용한다. 미리보기 공유는 인증된 개발 연결로 명시적으로 연다.
- 실행 관리 서비스가 컨테이너를 제어하며 앱이나 코딩 작업에 호스트 Docker 소켓을 노출하지 않는다.
- 코어가 검증한 개발 환경 프로파일을 기본으로 사용한다. 앱이 변경할 수 있는 설정과 관리 서비스만 변경할 수 있는 설정을 구분한다. 앱 저장소의 `initializeCommand` 같은 호스트 실행, 임의 호스트 마운트·특권·환경 변수 전달·인증 파일 접근을 그대로 허용하지 않는다.
- worktree는 소스 변경 충돌을 분리한다. 프로세스·파일·네트워크·DB 접근은 컨테이너와 OS·서비스 권한으로 별도 제한한다. 소유자의 코어 관리용 호스트 권한을 현업 앱 개발에 자동 승계하지 않는다.
- 작업별 자원 제한과 대기열을 둔다. 초기 수용 목표는 한 사용자의 동시 미리보기 4개, 무거운 빌드 1개다. 측정 전 성능 보장으로 표현하지 않는다.
- 자원 제한의 지원 조건과 실제 적용값을 확인하고 초과 시 동작을 시험한다. 환경 정지·삭제 후 프로세스·포트·임시 테스트 데이터의 정리 범위를 정하고, 유지할 소스·이력·데이터는 보존한다. 신뢰가 다른 여러 사용자의 보안 격리는 후속 범위다.
- 읽기와 수정 작업을 구분하고 같은 작업 트리의 충돌은 기존 자원 잠금과 분리된 작업 디렉터리로 처리한다.

앱 담당자는 허용된 권한과 자동 검증을 충족하면 첫 배포부터 직접 배포할 수 있다. 코어 담당자의 매번 수동 승인을 기본 절차에 넣지 않는다. 개발 요청을 운영 배포 요청으로 확대하지 않으며 명시된 요청 범위에서 실행한다.

배포 서비스는 검증 대상 소스와 실제 산출물의 일치, 대상 환경, 권한을 확인한다. 코드가 바뀌면 필요한 검증을 다시 수행한다. 앱 배포가 플랫폼·공식 앱 전체의 재빌드나 재시작을 요구하지 않게 한다.

배포 계약은 앱·환경, 소스/변경 식별값, 불변 산출물 digest, 계약·마이그레이션 버전, 검증 실행 결과와 실행 주체를 연결한다. 검증 서비스의 결과를 확인하며 LLM이나 앱이 작성한 성공 문구를 증거로 인정하지 않는다. 검증한 산출물을 그대로 승격하고 런타임 설정·대상 환경·권한을 배포 시 다시 확인한다. 검증 이후 소스·관련 계약이 바뀌거나 다른 환경의 근거를 제출하면 필요한 검증을 다시 수행한다.

배포 후 상태를 확인하고 실패 시 이전 앱 릴리스로 복구한다. 데이터 변경은 이전 버전과 공존 가능한 방식으로 수행하며 앱 이미지 복구와 DB 복구를 구분한다. 재시도가 중복 배포나 데이터 변경을 만들지 않게 한다. 이 앱 배포 경로는 기존 플랫폼 보호 브랜치와 릴리스 절차를 우회하는 경로가 아니다.

외부 배포 요청 ID와 결과는 배포 서비스가 PostgreSQL 등 해당 서비스의 내구성 있는 저장소에 기록한다. Workbench의 기존 `launch_id`는 Task 중복 생성 방지로 재사용하며 외부 배포의 중복 실행 방지와 구분한다. 응답 유실·서비스 재시작 후에는 기존 요청 상태를 먼저 조회하고, 결과가 불명확하면 확인 필요로 남긴다. 배포 상태를 관측하는 기능을 별도 Codex 계획·재시도 엔진으로 확대하지 않는다.

## 5. 단일 사용자 Workbench

### 유지할 기반

기존 공식 Codex app-server의 thread·turn·계획·승인·스킬·에이전트 실행을 사용한다. [Task와 native thread 투영](../apps/codex-console-api/src/codex_console/models.py), [실행 엔진](../apps/codex-console-api/src/codex_console/runtime.py), [템플릿](../apps/codex-console-api/src/codex_console/templates.py), [관측 기능](../apps/codex-console-api/src/codex_console/monitor.py)을 우선 재사용한다.

Workbench는 환경과 자원을 준비하고 native 상태를 보여준다. 별도 에이전트 계획·실행·재시도 엔진을 추가하지 않는다. 기존 단일 소유자 인증, SQLite, 독립 서비스·릴리스와 플랫폼 장애 시 복구 접근을 유지한다. 다중 사용자용 PostgreSQL 전환을 선행 조건으로 두지 않는다.

여러 앱·저장소·개발 환경을 기존 작업 모델에 연결한다. 허용된 소스 경로와 실행 환경을 서버가 확인하며 사용자 입력 경로를 그대로 호스트 권한으로 연결하지 않는다.

### Native 계약과 호환성

기존 CLI 버전·소비 스키마 검사를 재사용한다. 사용할 RPC마다 지원 CLI, 소비 스키마, 안정/실험 상태, 실행 위치·권한, 미지원 시 동작을 기록한다. 새 기능은 실제 사용하는 버전에서 확인한 뒤 연결한다. 공식 문서에 나온 기능을 모두 현재 사용 가능하다고 가정하거나 미지원 기능을 별도 실행 엔진으로 흉내 내지 않는다.

API 이름이 비슷해도 샌드박스 적용 여부와 권한 의미를 개별 확인한다. 호스트에서 실행되는 표면을 앱 개발용 샌드박스 명령으로 취급하지 않는다. 설정 필드의 상호 배타 조건과 운영 사용 제한도 소비 계약 검사에 포함한다. 호환성 오류는 분명히 표시하고 검사를 끄는 우회 경로를 만들지 않는다.

### 세션 경험

이번에는 선택 앱/저장소 연결·실행/중단/재개·실제 상태/오류와 기존 이력 보존에 한정한다. 아래 고급 탐색·모바일·표시 확장 중 아직 구현하지 않은 부분은 `ENH-001`로 보류하며 기존 구현은 유지한다.

- 앱·저장소별 목록, 검색, 고정, 최근 작업 접근을 제공한다.
- 진행 중·확인 필요·종료, 일반 작업·템플릿 실행을 구분한다.
- 세션 전환과 목록 복귀에서 작성 중 입력, 스크롤, 검색·필터와 선택 상태를 보존한다.
- 작업 경로·브랜치·미리보기·변경 내용·테스트 결과를 같은 작업 맥락에서 확인한다.
- 질문·승인·실패 등 사용자 조치가 필요한 상태를 명확히 표시한다.
- native 상태를 확인한 뒤 재개하며 화면 연결 끊김과 실제 실행 종료를 구분한다.
- 저장된 대화, 서버에 로드된 실행, 현재 turn, 이벤트 연결 상태를 구분한다. 기록이 존재한다고 실행 중으로 표시하거나 연결이 끊겼다고 작업 실패·재실행으로 처리하지 않는다.
- 좁은 화면·모바일·키보드 탐색을 검증한다.

### 에이전트 경험

Root와 하위 에이전트의 관계·역할·현재 활동·결과·오류·갱신 시각을 표시한다. 진행은 native 상태와 실제 단계에 근거하고 임의 완료율을 만들지 않는다.

중단은 지원되는 native 기능으로 전달하고 결과 상태를 확인한다. 이벤트 누락이나 오래된 관측은 미확인으로 표시하고 조회로 보완한다. Workbench가 별도 하위 에이전트를 자동 생성하거나 불확실한 작업을 중복 실행하지 않는다.

### 표준 명령 템플릿

아래는 전체 목표 목록이다. 이번에는 기존 검토·테스트와 새 앱의 최소 미리보기·배포·복구 연결만 완성하고 추가 템플릿·자동화는 `ENH-002`로 보류한다.

| 템플릿    | 동작                                                                      |
| --------- | ------------------------------------------------------------------------- |
| 코드 검토 | 지정 변경의 근거·문제·개선점을 보고하며 게시·병합은 별도 요청 범위로 확인 |
| 테스트    | 앱 계약과 변경 범위에 맞는 검사를 수행하고 결과 정리                      |
| 미리보기  | 해당 개발 환경을 실행하고 접근 주소·상태 확인                             |
| 배포      | 앱·환경·검증된 산출물 확인, 배포와 후속 상태 점검                         |
| 운영 점검 | 서비스·릴리스·오류·자원 상태를 읽어 진단                                  |
| 복구      | 명시된 대상과 범위에 맞는 검증된 복구 절차 수행                           |

입력값, 대상 앱·환경, 참조 지침·스킬, 검증 명령, 완료 조건을 버전으로 관리한다. 기존 템플릿 실행과 실행 당시 설정 보존을 확장한다.

| 실행 시 연결할 항목 | 계약                                                                                      |
| ------------------- | ----------------------------------------------------------------------------------------- |
| 의도·대상           | 현재 요청, 앱·환경, 저장소·작업 경로. 현재 선택으로 채운 값은 사용자가 확인 가능하게 표시 |
| 허용 동작           | 읽기·수정·실행 범위와 실제 도구 권한. 템플릿 문장이 실행 권한을 부여하지 않음             |
| 실행 기준           | 소스/변경 식별값, 계약·하네스·템플릿 버전, 참조 가능한 실행 당시 원본                     |
| 완료 근거           | 영향에 맞는 검사와 대상·버전·결과. 미실행·실패·불명확을 구분                              |
| 재개 정보           | 기존 Task·native thread, 마지막 확인 상태, 반복 전 조회해야 하는 외부 작업                |

이 항목은 기존 템플릿·Task·배포 계약에 연결하며 새 범용 워크플로 모델을 만들지 않는다. 기존 검토·테스트 템플릿 개선을 먼저 사용할 수 있게 하고 독립 앱 미리보기·배포·복구 연결은 해당 계약 준비 후 추가한다.

자연어와 선택 버튼으로 실행하고 현재 앱·세션에서 알 수 있는 값은 자동으로 채운다. 결과를 크게 바꾸는 모호함만 질문한다. 같은 실행 요청의 재시도는 중복 작업을 만들지 않으며 템플릿 수정이 과거 실행 조건을 바꾸지 않는다.

지침·스킬은 공식 파일과 발견·선택 방식을 활용한다. 실행 당시 참조 버전을 추적하되 파일 해시만으로 원문이 보존되었다고 주장하지 않는다. 템플릿은 기존 Codex 작업으로 실행하고 버전 있는 공통 SDK·CLI와 검증된 명령을 사용한다.

일관성은 동일한 문장 출력이 아니라 동일한 권한·계약·검증 절차와 확인 가능한 결과를 기준으로 평가한다. 일반 자연어 대화도 계속 사용할 수 있다.

### 자연어와 하네스

코어 개발자가 앱 템플릿, 지침·스킬, 공통 명령, 테스트·배포 계약을 관리한다. Workbench는 사용자가 이를 활용하도록 작업 맥락을 제공한다.

맥락에는 대상 앱·저장소·환경, 소스와 배포 버전, 작업 이력, 현재 요청, 하네스·SDK·템플릿 버전, 허용된 범위와 완료 기준을 포함한다. 저장소나 외부 문서의 내용이 실행 권한을 새로 부여하지 않게 한다.

현재 의도·대상·범위·완료 기준을 기본 맥락으로 제공하고 세부 계약·이력은 필요할 때 읽는다. 전체 계획·오래된 기록·스킬을 일괄 주입하지 않는다. 버전과 참조 가능한 원본을 연결하되 비밀정보나 프롬프트 원문을 이 문서 트리에 쌓지 않는다. 지원되는 native 지침 출처 정보는 선택을 관측하는 데 활용하며 실제 준수는 작업 결과로 확인한다. 재개 시 정책 변경과 진행한 작업의 충돌을 확인한다.

“이 앱 테스트해줘” 같은 생략은 선택과 이력으로 보완한다. 대상이 여러 개이거나 운영 변경 범위가 불명확할 때만 필요한 내용을 묻는다. 정책과 권한은 서버·실행 환경이 강제하며 LLM의 해석만으로 검증이나 권한을 우회하지 않는다.

작업 크기에 맞게 명세를 남긴다. 작은 수정은 요청·영향·확인 기준으로 진행하고, 앱 생성·API·데이터 변경은 사용자 시나리오와 권한·데이터 계약을 먼저 정한다. 배포·복구는 명시된 대상·버전·범위와 확인 근거를 연결한다. 이미 명확한 요청을 반복 승인받거나 요청하지 않은 기능으로 확대하지 않는다. 명세는 구현에서 얻은 사실과 조정하며 기존 코드 전체를 재생성하는 원본으로 취급하지 않는다.

이번 하네스 확인은 [VALIDATION.md](VALIDATION.md)의 대표 앱 흐름에서 대상·권한·실제 결과를 확인하는 데 한정한다. 광범위한 표현별 반복과 변경 전후 품질 벤치마크는 `ENH-003`으로 보류한다. LLM의 자기평가만으로 완료 처리하지 않으며 기존 native 실행을 활용한다.

기존 구독 인증 방식을 유지하고 인증 저장소와 작업 대화·코드·메모리의 접근 경계를 보존한다. 새 계정 풀 운영은 ENH-008로 보류하며 API 과금으로 자동 전환하지 않는다.

배포된 업무 앱의 AI 기능은 공통 AI Gateway 계약을 따른다.

### 운영 모니터링

이번에는 미리보기·설치 상태·적용 버전·실패/미확인과 복구 결과를 확인하는 최소 연결만 수행한다. 아래 상세 서비스/자원 표시와 고급 대시보드 확장은 `ENH-002`로 보류한다.

기존 읽기 전용 관측을 확장해 Codex·템플릿 실행 서비스, 앱·미리보기 상태와 배포 버전, 진행·대기·확인 필요 작업, 자원 사용, 마지막 관측 시각을 표시한다. 확인하지 못한 버전과 상태를 추정하지 않는다.

조치가 필요하면 해당 앱·환경을 운영 점검·복구 템플릿에 연결한다. 관측만으로 재시작이나 배포를 자동 실행하지 않는다. 실행 서비스 장애와 관리 화면의 마지막 관측을 구분한다.

## 6. 이행과 완료 기준

서로 독립인 결과는 먼저 완성해 사용할 수 있게 한다. 정확한 작업 의존성·하위 작업·상태는 [WORK_ITEMS.md](WORK_ITEMS.md)가 소유하며 아래 흐름은 전체 직렬 단계가 아니다.

| 작업 흐름                     | 먼저 확인할 결과                                                                   | 후속 연결                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 필수 경로의 정책 전환         | 실제 충돌하는 지침만 해소하고 핵심 계약 보존                                       | 대표 앱 흐름의 시작·재개 확인. 전역 정리·반복 평가는 ENH-003      |
| 기존 앱 발견·Workbench 사용성 | 목록 누락·제한 이유, 세션 탐색·전환·재개, 기존 검토·테스트 템플릿과 읽기 전용 관측 | 독립 앱 런타임 전체를 기다리지 않고 기존 저장소에서 검증·사용     |
| 독립 앱 시범 적용             | 정의·릴리스·설치 계약, 앱 세션·SDK, 검증된 개발 환경·두 시험 앱                    | UI 앱의 등록→미리보기→배포→복구를 먼저 확인하고 DB·권한 앱에 확장 |
| 기본 실행 환경                | 지원 로컬·서버의 경로·권한·자원 제한·정리 확인                                     | 병행 부하·수용량 측정은 ENH-004로 보류                            |
| Workbench 새 앱 연결          | 준비된 개발 환경과 기존 Task 연결                                                  | 검증된 앱 배포·복구와 상태 관측 연결                              |
| 공식 앱 경계·분리             | 소유·공통 API·데이터 경계 조사부터 수행                                            | 시범 적용 결과를 반영해 공식 앱 묶음의 빌드·릴리스 분리           |
| 이전·인수                     | 앱별 이전·복구, 변경된 계약과 대표 경로의 회귀 확인                                | 구조 작업 흐름의 통합·미검증 경계 확인과 소유 문서 정리           |

전역 지침 전환의 완료를 기존 앱의 작은 수정이나 독립 조사 전체의 선행 조건으로 두지 않는다. 각 작업에서 충돌하는 규칙은 먼저 해소하고 해당 경로의 지침·검증 근거를 남긴다. 같은 파일·계약을 변경하는 작업은 순서를 조정한다. 별도 에이전트 병렬 실행을 요구하는 계획은 아니다.

UI 중심 시험 앱과 DB·권한을 사용하는 시험 앱으로 계약을 확인한 뒤 기존 앱을 이전한다. 기존 ID·주소·사용 권한·데이터를 보존한다. 원격 프로젝트는 과거 누락 사례의 호환성 검증 근거이며 해당 프로젝트의 변경·배포를 자동으로 포함하지 않는다.

필수 구조의 영향 검사·대표 흐름은 [일괄 검증 원칙](VALIDATION.md#2026-10-10-검증-일괄-수행-원칙)에 따라 최종 통합 시점에 모은다. 중간에는 진행을 막는 오류와 구체적인 치명적 경계의 최소 확인만 수행한다. 이번 범위의 완료 여부는 위 필수 항목으로 판단하고 `FOLLOW_UP_ENHANCEMENTS.md`와 `APP_ISSUES.md`의 보류 항목을 전체 완료 조건에 포함하지 않는다. 문서 작성 완료나 기존 테스트 통과를 구조 구현 완료로 표시하지 않으며, 필수 경계가 미완료이거나 치명적 결함이 남으면 완료로 판정하지 않는다.

## 7. 조사에 사용한 공식 사례

아래 자료는 대화 중 조사한 설계 근거다. 외부 제품을 도입하겠다는 결정은 아니며 실제 구현 시 사용하는 버전의 공식 지원 범위를 확인한다.

추가 웹 재검토의 자료 20개와 적용 한계는 [REVIEW.md](REVIEW.md) 7절에서 관리한다.

- [Backstage Software Catalog](https://backstage.io/docs/features/software-catalog/): 소스의 앱 정의와 카탈로그 투영을 구분하는 참고 사례.
- [Forge 개발 환경](https://developer.atlassian.com/platform/forge/environments-and-versions/): 앱별 개발 환경 분리 사례. 다중 개발자 지원은 MIY의 후속 범위로 둔다.
- [Forge Custom UI iframe](https://developer.atlassian.com/platform/forge/custom-ui/iframe/): 호스트와 앱 UI의 연결·격리 사례.
- [Forge AI Plugin](https://developer.atlassian.com/platform/forge/ai-development-toolkit/forge-ai-plugin/): 플랫폼 지침·스킬·템플릿·문서 도구를 함께 제공하는 사례.
- [Shopify 앱 인증](https://shopify.dev/docs/apps/build/authentication-authorization/id-tokens): 임베디드 앱의 별도 인증 문맥을 전달하는 참고 사례.
- [Codex App Server](https://learn.chatgpt.com/docs/app-server): Workbench가 재사용할 native 실행·질문·승인·상태 인터페이스.
