# 공식 앱 분리 경계와 이행 설계

`OFF-001`의 코드 조사와 `OFF-002` 구현 입력이다. 시작 HEAD는 `449d1417afbf6a2eb978c1465c765e26ef43c5dc`, 조사 대상은 2026-10-06 현재 로컬 작업 트리다. 아래의 **현재**는 실제 import·모델·라우터·큐 등록에서 확인했고, **목표/단계**는 아직 배포하지 않은 설계다. 독립 서비스·DB 이전 완료를 뜻하지 않는다. 진행 상태와 실행 결과는 [작업 목록](WORK_ITEMS.md), [검증](VALIDATION.md)이 소유한다.

## 판단과 가장 작은 구현 단위

공식 앱은 우선 **하나의 suite**로 분리하는 것이 맞다. PMS·Docs·회의·녹음·캘린더를 각각 서비스로 나누면 현재의 교차 외래키·같은 트랜잭션·권한 판정을 동시에 재설계해야 한다. 반면 포털은 세션·회사 입장·앱 탐색·공통 탐색 틀을 담당하고 공식 업무 화면은 suite UI가 담당하도록 나누면 개인 앱의 빌드·장애와 공식 앱의 릴리스를 분리할 수 있다.

가장 작은 첫 구현은 **공식 앱 전용 composition root와 UI 빌드 대상**을 추가해 기존 화면과 경로를 재사용하는 것이다. 이것만으로 API·worker·DB의 독립성이 생기지는 않는다. 실제 트래픽 전환은 아래 등록 충돌, 인증 위임, 원본 ACL, outbox 소비 계약을 검증한 다음 진행한다. 초기에는 동일 저장소에서 명확한 디렉터리·빌드·쓰기 소유권을 만들고, 저장소 자체의 분리는 그 다음 결정해도 된다.

현재 [apps/official-suite](../apps/official-suite/README.md)에 0단계 UI composition·별도 Nx/Vite target과 API/model/worker 소유권 manifest를 구현했다. 공식 12개 앱의 순서·ID는 공통 계약이 소유하고 기존 웹의 임시 공개 모듈 adapter를 두 root가 함께 읽는다. suite에서 legacy로 향하는 명시적 bridge 한 방향만 남겨 프로젝트 순환을 만들지 않는다. 공통 registry factory와 shell 상태 계산은 기본 전체 앱 조립에서 분리했다. 앱 스코프는 런처·직접 개인 앱 host 경로에 적용하고 기존 포털의 전체 목록은 유지한다. 다만 업무 소스의 물리 경로, 공용 UI·인증·번역·assets·Vite 설정은 기존 웹의 공개 진입점을 거치는 임시 bridge다. 따라서 아래 0단계의 **shared UI/contracts만 의존** 조건은 아직 최종 달성이 아니며 독립 서비스 완료로 표시하지 않는다. DM/Calendar 위젯·알림·공통 realtime과 후속 writer 전환도 남아 있다.

[독립 앱 계약](../apps/api/src/miy_api/domains/independent_apps/README.md)과 이번 generic host를 재사용하되, 현재 개인 앱 계약만으로 공식 suite가 이식 가능하다고 가정하지 않는다. 실제로 `independent_apps/service.py:register_definition`은 기존 `APP_CONTRACT_BY_ID`와 충돌하는 ID를 거부하고, 기존 `/api/v1/pms` 등은 앱 세션 토큰을 사람의 로그인 토큰으로 받아들이지 않는다. 이 두 경계를 우회하는 임시 alias/토큰 전달을 추가하지 않는다.

## 테이블 쓰기 소유권

첫 API 분리에서 같은 PostgreSQL 클러스터/DB를 사용할 수 있다. 이는 임시 호환 구간이며 각 테이블의 writer는 하나다. 서비스별 login role, migrator role, SELECT-only compatibility view를 구분한다. suite role에 플랫폼 테이블 전체 DML을 주거나 플랫폼이 업무 모델을 계속 수정하는 구성을 완료로 인정하지 않는다.

| 목표 writer                              | 현재 테이블/모델 집합                                                                                                                                                                                                                                                           | 읽기·변경 경계                                                                                                                                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### projection outbox와 원자성

현재 `search/default_index_hook_adapters.py`, 앱별 `rag_sync.py/search_hooks.py`는 원본 변경과 projection 작업을 같은 Session에서 연결한다. HTTP enqueue를 추가하는 것만으로 분리하면 원본 commit 후 요청 유실이 생긴다.

1. suite 소유의 durable source outbox를 원본 transaction에 기록하는 migration을 만든다. 각 event는 기존 `app_id/resource_type/resource_id`, 원본 revision, 권한 revision, 생성/수정/삭제 종류, 명시적 schema version과 멱등 event ID를 가진다. 원문이나 토큰을 이벤트에 과잉 복사하지 않는다.
2. 플랫폼 consumer가 event ID를 유일하게 받아 현재 projection event/head/job을 생성한다. suite는 acknowledged cursor를 저장하고 응답 유실 시 같은 ID로 상태 조회/재전송한다. 요청 순서만으로 최신 상태를 판정하지 않는다.
3. 기존 projection watermark·generation pair·partition ID를 cutover manifest에 고정한다. 기존 job drain, source outbox 시작점, tombstone·권한회수 전달 완료를 검증한다. dual-read 비교는 가능하나 두 publisher가 같은 resource/version을 별도 작업으로 중복 확정하지 않는다.
4. 그 후 업무 role의 공통 projection 테이블 DML을 회수한다. 이 단계 전에는 API 서비스 분리를 완성으로 표시하지 않는다. 재색인 실패 시 이전 active generation을 유지하고 원본 ACL 검사는 항상 현재 suite에서 한다.

## 인증·라우팅·ID 보존

현재 `/apps/pms`, `/apps/docs` 같은 앱 ID/경로, 원본 UUID, 문서 page/link-share, notification deep link, AI workload/tool/scope ID, retrieval resource type/partition 식별자는 유지한다. URL rewrite로 새 `pms-v2` ID를 만들어 기존 회사 정책과 사용자 즐겨찾기/권한이 끊기는 방식을 쓰지 않는다. DM/Calendar는 현재 core capability라는 사실을 보존한 채 실행 위치를 옮길 수 있으며 이번 조사만으로 임의의 새 launcher 앱 ID를 만들지 않는다.

공식 suite는 하나의 불변 이미지 릴리스로 여러 기존 앱을 제공한다. 따라서 다음의 **core owner 전용 migration 계약**이 필요하다.

- 기존 logical app ID별로 실행 소유자(`legacy` 또는 `official-suite`), suite release/installation, 해당 앱의 entrypoint를 저장한다. 한 ID에는 한 활성 소유자만 둔다. UI/API/worker 소비자는 같은 route generation을 읽고 버전 충돌 시 전환을 거부한다.
- personal 정의 등록의 기존 ID 충돌 거부는 유지한다. 일반 앱 등록 API에 임의 override 옵션을 열지 않는다. suite artifact를 앱마다 재빌드하지 않고 하나의 검증된 digest에 여러 기존 app mount를 연결한다.
- 포털 URL은 유지하고 route resolver가 내부적으로 해당 설치를 연다. 이미 열린 문서/협업 세션은 release generation에 묶고 drain 또는 명시적 재접속을 수행한다. 이전 API와 새 UI가 우연히 섞이지 않도록 호환 범위를 확인한다.
- suite는 기존 generic host의 exact origin/source·PKCE·일회용 code·폐기 가능한 app session을 재사용한다. 기존 product API는 이 토큰을 사람 토큰으로 받아들이지 않는다. core가 승인한 **app 제한 서버 위임**을 추가하고, 각 요청에서 installation admission·사용자 활성/세션·회사 앱 정책을 확인한 뒤 suite가 원본 ACL을 다시 확인한다. 헤더의 임의 user ID, 브라우저 원본 로그인 bearer 복사, service-admin 권한 사용은 금지한다.
- 위임 API는 원본 ACL batch query, 앱별 허가된 tool 실행, bounded directory 조회, content grant, source projection snapshot 등 필요한 계약만 연다. 요청/결과에 contract version·resource revision·trace/operation ID를 포함하고 timeout/크기/재시도 범위를 고정한다. 각 write는 기존 approval/audit/idempotency와 연결한다.

## 구현 착수 시 필수 회귀 증거

- API route/OpenAPI·generated client·기존 `/apps/*` deep link·브라우저 새로고침·모바일/키보드 탐색이 같은 logical ID로 동작한다.
- 회사 앱 disable, 사용자 disable/session revoke, 그룹 제거, PMS 공간 제외, Docs/Whiteboard 공유 회수, DM 비참가자, 회의 비참석자, Files private→company와 삭제를 원본 API·검색·RAG·AI tool·realtime·content grant에 모두 적용한다.
- 승인된 동일 AI write/메일 전송/녹음 게시 요청의 응답 유실 뒤 재조회·재시도에서 결과가 하나이며, unapproved 또는 다른 resource revision은 거부한다.
- worker restart/beat 재발행, queue drain, projection event 순서 역전·중복·tombstone, source timeout, generation mismatch에서 누락·권한확대 없이 복구한다.
- 읽기 전용 shadow와 canary는 데이터 삭제나 운영 전환 권한이 아니다. 실제 활성화·배포는 구체적인 artifact/route generation/DB 호환·백업 증거에 대한 별도 승인 후 진행한다.

기존 테스트 소유자는 [API tests](../apps/api/tests), [worker tests](../apps/worker/tests), [앱 경계 브라우저 검사](../apps/web/e2e/app-boundary-smoke.spec.ts), 각 app-module의 API/경로/권한 테스트다. 구현된 경계에 맞춰 affected consumer 전체를 선택하고, 새 원격 adapter 계약·실패/취소·이중 writer 방어는 새 의미 있는 검사로 추가한다. 이 문서 작성에서는 AST/코드·모델·큐 조사를 수행했으며 공식 suite의 원격 배포·권한 DML 감사·운영 큐 drain은 실행하지 않았다.

## 현재 결정과 남은 조건

`OFF-002B`의 첫 구현은 [공식 API wheel/entrypoint](../apps/official-suite/api/README.md), platform/official router 소유 registry, 기존 순서의 legacy 합성과 worker task/Beat 소유 catalog다. 새 API profile은 health/OpenAPI 관찰만 가능하고 업무 요청·runtime 초기화를 거부한다. 실제 auth session 갱신, projection/outbox, AI 승인, 메일/녹음/파일 cleanup 등 공유 쓰기와 다음 단일 writer/routing/role/worker 전환 순서는 [API 전환 owner](OFFICIAL_API_CUTOVER.md)가 소유한다. 별도 서비스 image와 운영 활성화는 아직 구현 완료가 아니다.

[ADR 0012](../adr/0012-company-app-access-without-workspaces.md)의 한 배포=한 회사, 사용자·그룹·앱 입장·리소스 ACL 의미를 유지한다. 그 ADR의 과거 개발 데이터 초기화는 이번 작업의 삭제 권한이 아니다. 폐기된 ADR 0006·0007·0011을 재활성화하지 않는다.

[앱 플랫폼 소유 문서](../docs/domains/app-platform/README.md)의 `miy-app` 공통 릴리스와 DM/Calendar core 배치는 현재 구현의 설명이다. 본 문서는 이행 설계의 소유자이며 현재 runtime 사실을 중복 정의하지 않는다. 실제 composition/deployment 계약 변경 시 해당 owner 문서와 검사를 함께 갱신한다.

`OFF-001`의 의존·소유권·전환 설계는 위와 같이 구체화했다. `OFF-002` 물리 분리의 선행 조건인 검증된 앱 release lifecycle, 공식 ID 전환 계약, 제한된 인증 위임, 원본 ACL 원격 계약, outbox/queue 단일 writer 전환은 아직 구현·검증해야 한다. 이번 문서만으로 공식 suite 독립 배포를 완료로 선언하지 않는다.
