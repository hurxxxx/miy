# 공식 API 서비스 전환 계약과 다음 구현

이 문서는 `OFF-002B`의 runtime activation·단일 writer 전환 설계를 소유한다. 소스/업무 경계 전체는 [공식 앱 조사](OFFICIAL_APPS.md), 현재 API artifact 실행 계약은 [공식 API owner](../apps/official-suite/api/README.md), 진행·검증 결과는 [WORK_ITEMS](WORK_ITEMS.md)와 [VALIDATION](VALIDATION.md)이 소유한다. 구현된 내부 인증 bridge와 아래 후속 전환 계획은 운영 schema 적용이나 승인된 배포를 뜻하지 않는다.

## 현재 구현과 활성화 경계

- Docs/PMS/회의는 명시적으로 준비한 원본 Session에서 업무 변경·회사 기본 파티션 binding·실제 outbox만 같은 transaction에 저장하고, 코어가 별도 Session에서 동일 event ID/digest를 수락하는 경로를 구현했다. 새 migration `official_partition_20261007`의 두 최소 capability는 각각 원본·코어 COMMIT까지 현재 metadata SHARE를 유지한다. setup 응답 유실은 저장한 UUID만 조회하고 재할당하지 않는다. prepared Core의 즉시 job 발행은 억제하지만 live Beat의 pending 발견까지 막지는 않는다. 집중 실제 PG70과 기존 guard90/Recording/role/migration/legacy의 넓은343 PASS·실패한 fixture4개 교정 뒤102 PASS, 최종1,101개 불변·이전25 migration 보존을 확인했다. 정확 실행과 중복은 [VALIDATION](VALIDATION.md)이 기록하고 [projection owner](../apps/api/src/miy_api/domains/official_apps/PROJECTION.md)가 구현 계약을 소유한다. 이는 내부 비활성 조립이며 전체 제한 Source HTTP/auth/ACL/audit·Files/Planner·broker/Beat·서비스 전환은 필수 잔여다.

- [platform registry](../apps/api/src/miy_api/platform_api_registry.py)와 [official registry](../apps/api/src/miy_api/official_api_registry.py)가 HTTP/WS router의 소유·공개/보호 분류·기존 등록 순서를 가진다. [legacy assembler](../apps/api/src/miy_api/api_registry.py)는 두 목록을 기존 순서로 조립하며 같은 router 객체를 중복 소유하면 거부한다. 기존 handler·`require_current_user`·입장·ACL·AI workload를 복제하지 않는다.
- `miy_api.main:app`은 기존 monolith runtime이다. `miy_api.platform_main:app`과 별도 wheel의 `miy_official_api.main:app`은 **inactive composition**이다. HTTP 업무 요청 503, WS 1013, readiness 503이며 활성화 환경변수가 없다. `/healthz`의 200은 프로세스 응답만 뜻하고 `activation: inactive`를 함께 표시한다. 새 artifact는 기존 DB 초기화·seed·자동 migration, MinIO, LLM/OPF/RAG, Hermes socket, Docs/Whiteboard hub를 시작하지 않는다.
- [공통 queue 계약](../apps/api/src/miy_api/core/worker_queue_contract.py)이 28개 task·12개 모듈의 소유를 명시한다. 기존 legacy worker는 전체 task와 Beat9개를 유지하고, 별도 플랫폼·공식 profile은 각각 task14개·Beat6/3개와 서로 겹치지 않는 queue를 가진다. 새 profile은 등록 검사만 가능하며 Worker/Beat/발행/직접 실행을 항상 거부한다. matching wheel3개와 실제 offline import를 검증했으며 새로운 consumer는 시작하지 않았다. [worker owner](../apps/worker/README.md)가 artifact와 미완료 활성화 조건을 소유한다.
- 공식 wheel은 같은 checkout의 `miy-api` 호환 wheel에 의존한다. 현재 공통 wheel에는 legacy entry와 모든 domain source가 남는다. 이는 소스·자격증명의 완전한 분리나 악의적인 운영자에 대한 격리가 아니다. 별도 비활성 API image는 아래의 고정 입력으로 검증했다. 전체 서비스의 최소 DB role, 운영 실행 identity·entry 고정과 라우팅 전환은 아직 남는다.
- [공식 인증 bridge](../apps/api/src/miy_api/domains/official_apps/README.md)는 core-approved `official_app_bindings`와 현재 앱 세션을 검증해 기존 `AuthContext`를 읽기만으로 만든다. RouterSpec의 서버 소유 logical app 범위로만 연결하고 Docs/PMS 원본 ACL을 보존한다. 사람 로그인 토큰은 suite에 전달하지 않는다. HTTP adapter는 구현됐지만 shared DB 조회를 remote introspection/최소 권한 DB role로 대체하지 않았고, WS·content/search 경계도 아직 남는다. 기존 inactive gate와 단일 legacy writer는 유지한다.
- [writer fence](../apps/api/src/miy_api/domains/official_apps/writer.py)는 `official.suite` 단일 scope를 사용한다. 현재 선언된 공식 업무 원본 **88개 전체**가 고정 CHECK/FK·statement guard의 보호를 받는다. `official_source_writer_20261007`은 이전 revision을 보존한 frozen19→88 migration이다. 외부 효과 직전에는 같은 source guard를 해당 transaction에서 재획득하고, DB commit 결과가 불명확하면 원본 객체·spool을 보존한다. 실제 PostgreSQL 최종210개와 독립 리뷰를 마쳤지만 원본 guard가 accepted postcommit 효과·worker/queue/Beat를 모두 보호하는 것은 아니다. `official-suite` owner 전환은 계속 항상 거부한다.
- [고정 projection 전달 계약](../apps/api/src/miy_api/domains/official_apps/PROJECTION.md)은 Docs/PMS/Meeting/Files의 원본 변경을 append-only source outbox로, Core 수락을 별도 receipt로 기록한다. 원본88개와 transport1개를 구분하며 source 역할은 outbox SELECT/INSERT만 받고 Core projection/receipt/job DML은 받지 않는다. 기존 네 hook의 같은 transaction bridge와 actual PG240·독립 리뷰를 마쳤다. Source revision과 Core version·watermark는 별개다. Docs 신규grant/meeting fan-out의 visibility 생산점4곳도 actual PG78·125입력·이전23migration 불변으로 연결했다. 구형 Docs scope/RAG/keyword의 Core repair도 source SELECT만으로 실제 event와 origin/target receipt를 원자 저장하며 actual PG 238개와 독립 리뷰를 통과했다. 최대 100개·processing 거부·동일 origin ID 복구를 유지한다. 새 consumer나 official runtime은 활성화하지 않았으며 구버전 worker drain·partition 생성·Files extraction 역방향 쓰기·source-only service wiring은 필수 후속이다.

- Recording 기본 HTTP는 기존 네 task의 legacy Canvas를 유지한다. 발행/COMMIT 응답 유실 시 원 attempt·오디오를 보존하고 두 재시도의 현재 권한 검사·reset·attempt를 한 COMMIT으로 처리한다. 뒤의 managed source command/Core publication 비활성 로컬 구현과 actual PG authority95·managed37·현재 schema legacy125 검증을 완료했다. 기본 API나 공식 profile을 자동 전환하지 않는다. 실제 서비스 반영·remote 취소/unknown 조정·trusted broker/Beat 활성화는 별도 미완료 경계다.

## 구현된 transaction writer fence

[Alembic revision](../apps/api/alembic/versions/official_writer_fence_20261006.py) `official_writer_fence_20261006`은 `official_auth_binding_20261006` 다음이다. `official_runtime_ownership`에 scope·owner·generation·artifact·active/draining 상태를 두고, `official_runtime_transitions`에 요청 UUID·요청 hash·현재 관리자/원본 세션 ID·전후 상태·사유를 같은 transaction으로 기록한다. 초기 행은 `official.suite / legacy / generation 1 / active`다. 초기 artifact는 검증된 image가 없으므로 `NULL`이며, 가짜 digest를 만들지 않는다. 이 revision은 아직 미게시·미배포여서 최초 공지 pilot의 scope를 현재 공식 묶음 계약에 맞춰 정정했다. 이미 적용된 사용자 migration을 고친 것이 아니다.

보호 source의 `writer_scope`는 `official.suite` 고정 CHECK와 ownership FK를 갖는다. 기존 행에는 서버 기본값을 채우고 기존 ORM·API 응답 계약을 유지한다. FK는 원본/제어 행의 무결성과 data restore의 parent-before-child 의존성도 명시한다. 공용 `public.miy_guard_official_source_writer`를 호출하는 statement-level `BEFORE INSERT / UPDATE / DELETE / TRUNCATE` trigger가 ownership 행을 `FOR SHARE`로 잠그고, 그 transaction에 고정된 `{scope, owner, generation, artifact}`를 현재 상태와 정확히 비교한다. trigger 인자는 migration이 고정하며 다른 scope는 거부한다. 0행 update, ORM flush, SQLAlchemy bulk, 직접 SQL, COPY도 같은 경계를 거친다. HTTP middleware나 caller의 commit 규약에 의존하지 않는다. PostgreSQL의 `BEFORE TRUNCATE`는 대상 table을 비우기 전에 실행한다. ([trigger](https://www.postgresql.org/docs/17/sql-createtrigger.html), [TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html))

현재 table inventory와 model mixin의 원본은 [writer_contracts.py](../apps/api/src/miy_api/domains/official_apps/writer_contracts.py)다. migration은 당시 목록의 고정 snapshot을 보유해 미래 runtime import에 따라 과거 schema가 바뀌지 않게 한다. 검사는 inventory·Docs 모델 전체·ORM의 scope column/CHECK/FK·migration snapshot·실제 PostgreSQL trigger의 table/event/인자/권한을 함께 비교한다. 새로운 Docs 모델을 추가하며 fence를 빠뜨리면 검사에서 드러난다.

### 공식 묶음의 단일 소유권과 Docs 쓰기 목록

공식 앱은 현재 한 API artifact로 릴리스하므로 owner/generation도 `official.suite` 하나다. 앱별 서비스를 분리하는 `FUT-003` 이전에 multi-scope transaction engine을 추가하지 않는다. 실제 [Recording→Docs 발행](../apps/api/src/miy_api/domains/recording/service.py)은 문서·페이지와 RecordingPublication을 같은 transaction으로 commit한다. Docs는 `media_files`, `usage_events`, `audit_logs`, `retrieval_partitions`, `retrieval_projection_heads/events`, `search_index_jobs`, `rag_sync_jobs`에도 같은 Session에서 쓰기를 연결한다. 이들은 플랫폼 소유를 유지한다. source trigger가 실패하면 같은 transaction의 pending 변경도 rollback되지만, source DML 없는 projection 재계산·audit/no-op 요청·worker의 별도 transaction까지 차단하는 구조는 아니다. 검색/RAG consumer의 원본 조회를 새 서비스 API로 바꾸지도 않았다. media 연결/삭제 행은 같은 transaction에 있고 MinIO 삭제는 commit 이후이므로 원본 거부 시 그 이후 삭제로 진행하지 않지만, 이미 commit한 요청의 지연된 객체 삭제는 별도 generation fence가 필요하다.

`bind_transaction`은 코어가 이미 승인한 실행 identity를 `SET LOCAL`과 같은 transaction-local 설정으로 고정한다. 현재 generation을 조회해서 오래된 실행에 자동 채택시키지 않으며, 한 transaction의 다른 identity 재바인딩도 거부한다. 아직 수정하지 않은 legacy caller는 정확히 `legacy / 1 / NULL`로 해석한다. 따라서 평상시 기존 caller는 동작하고, drain 또는 generation 변경 이후에는 재시작·명시적인 runtime identity 연결 없이 자동 복귀하지 않는다. commit·rollback 및 설정 이전 savepoint로 rollback하면 설정이 해제된다. ([SET LOCAL](https://www.postgresql.org/docs/17/sql-set.html))

`transition`은 실제 DBAPI autocommit을 거부하고 `READ COMMITTED` transaction만 받는다. `REPEATABLE READ`/`SERIALIZABLE`에서는 ORM을 refresh해도 같은 snapshot 안의 회수 전 권한을 계속 볼 수 있고, autocommit에서는 ownership/audit의 원자성이 사라지기 때문이다. caller의 isolation을 바꾸거나 기존 transaction을 commit해서 우회하지 않는다. 이어서 현재 non-impersonated platform admin의 원본 로그인·역할을 검사하고 같은 ownership 행의 `FOR UPDATE` 잠금을 얻는다. 기존 source transaction의 공유 잠금이 끝날 때까지 기다린 뒤 **관리자 권한을 다시 검사**한다. 전체 expected snapshot이 일치해야 generation을 한 단계 증가시키며, audit와 함께 caller transaction에서 commit한다. 응답 유실은 같은 UUID/같은 payload의 저장된 결과로 수렴하고, 같은 UUID의 다른 payload나 오래된 snapshot은 거부한다. replay도 현재 권한 검사를 생략하지 않는다. 이 내부 API에는 HTTP/CLI 노출, 자동 commit, 운영 전환 설정이 없다.

서로 다른 source writer의 공유 잠금은 공존한다. controller가 먼저 기다리는 source 하나를 해제해도 나머지가 끝날 때까지 CAS는 완료되지 않는다. source mutation과 controller 전환을 한 transaction에 섞거나 source/control table의 잠금 순서를 바꾸면 lock upgrade 또는 deadlock이 생길 수 있다. controller는 source DML 없는 전용 transaction에서 실행해야 한다. PostgreSQL이 deadlock을 거부하면 **전체 실패 transaction을 rollback**하고 현재 owner·요청 UUID 결과부터 재조회한다. 잠금을 우회하거나 부분 commit·generation 자동 채택으로 복구하지 않는다. savepoint 이후 얻은 잠금은 그 savepoint rollback 때 해제된다. ([잠금과 deadlock](https://www.postgresql.org/docs/17/explicit-locking.html))

### 별도 LOGIN 역할의 준비와 명시 강화 전환

권한 계약의 owner는 [공식 앱 core README](../apps/api/src/miy_api/domains/official_apps/README.md#restricted-postgresql-writer-authority)와 [writer_roles.py](../apps/api/src/miy_api/domains/official_apps/writer_roles.py)다. `official_writer_roles_20261006`은 기존 fence 다음 migration이며 OID+역할명·owner·generation·artifact·승인자/세션의 변경 불가 매핑과 private `SECURITY DEFINER` 함수만 추가한다. migration만으로 기존 12개 trigger를 교체하거나 서비스 역할의 권한을 바꾸지 않는다. 역할·비밀 발급, 운영 DB grant, HTTP/환경변수 활성화도 없다.

별도 LOGIN/NOLOGIN 역할을 사전 준비한 core caller만 exact ownership snapshot으로 `prepare_principal`, `install_role_guard`, `revoke_principal`을 호출할 수 있다. 원래 관리자 resolver를 재사용하고 ownership lock 대기 후, grant/trigger DDL 대기 후 현재 세션·역할을 재검사한다. 이전 snapshot이 권한 회수를 가리지 않도록 이 준비 작업은 READ COMMITTED transaction만 허용한다. PUBLIC·열별 권한·sequence·security-definer 실행·재위임·`session_replication_role` 등의 명시 parameter 권한·소유권·membership을 포함한 예상 외 권한은 자동 수리 없이 거부한다. 실제 trigger 교체는 exact **draining** 상태에서만 한 savepoint로 수행하며 승인 철회/오류 시 DDL·grant·audit도 rollback한다. 런타임 LOGIN의 새 준비는 명시된 19개 원본 SELECT/INSERT/UPDATE/DELETE만 받고 control/mapping/audit 읽기·수정, trigger 변경, TRUNCATE 권한을 받지 않는다. NOLOGIN 함수 owner만 잠금에 필요한 control/mapping SELECT/UPDATE를 갖고 membership과 schema CREATE는 없다.

교체 후 trigger는 `session_user`의 현재 OID와 이름을 둘 다 비교한다. `current_user`/임의 GUC를 신뢰하지 않으며 고정 `pg_catalog,pg_temp` search path와 qualified table을 사용한다. 기존 열린 세션도 generation/artifact 전환·회수 뒤에는 쓰지 못하고, 같은 이름으로 재생성한 역할도 예전 매핑을 재사용하지 못한다. 매핑은 회수만 가능하며 다시 활성화·수정·삭제할 수 없다. 다만 privileged core/DB owner는 계속 신뢰 경계 안에 있고, core가 기록한 artifact 연관 자체는 배포 검증/서명 증거를 대체하지 않는다. 함수에 연결된 trigger가 남은 상태의 자동 schema downgrade는 거부한다.

**이 역할로 공식/legacy 서비스 전체를 실행할 수 없다.** 현재 source 19개만의 경계이며 기존 인증·ACL 조회, 플랫폼 outbox/audit/projection, 나머지 69개 업무 table과 worker/외부 부작용은 아직 연결되지 않았다. 원본 DML 권한은 사용자별 ACL을 대체하지 않는다. 별도 credential의 실제 runtime 연결·검증 및 routing/worker drain이 준비되고 운영 전환이 승인되기 전에는 실행에 제공하지 않는다. 기존 cooperative GUC guard는 기본값으로 유지되며 역할 준비만으로 안전한 앱 실행이 되지 않는다. `official-suite` owner는 기존 CAS에서 계속 거부한다. 모든 실제 역할/grant/전환 검사는 새 disposable PostgreSQL에서만 수행하며 운영 상태는 변경하지 않았다.

HTTP 요청의 [공용 DB Session dependency](../apps/api/src/miy_api/core/db.py)는 PostgreSQL SQLSTATE/pgcode `55000`과 driver `diag.message_primary`의 정확한 `official_writer_fenced` 또는 `official_writer_control_missing` 조합만 구분한다. 해당 transaction을 rollback한 뒤 기존 다국어 오류 envelope의 `{detail, code: "official_apps.writer_unavailable"}`와 HTTP 503, `X-MIY-Error-Code`, `Retry-After: 5`를 반환한다. SQL·파라미터·driver 원문은 응답에 포함하지 않으며, 다른 DB 오류와 일반 예외는 기존대로 전파한다. 재시도 대기 표시는 5초 뒤 복구 완료를 보장하거나 비멱등 요청을 자동 재전송하는 기능이 아니다.

현재는 운영용 identity 설정·drain·복구 명령을 제공하지 않는다. runtime identity, 모든 원본·worker·외부 부작용의 fence, 최소 권한 DB role, 상태 관측/복구 경로가 연결되기 전에는 전면 적용이나 activation을 허용하지 않는다. schema downgrade는 기존 원본을 보존하는 migration 호환 검사에만 사용하며, runtime/image rollback에서 ownership 세대를 초기화하거나 audit를 지우는 수단으로 사용하지 않는다.

### Personal Widgets 두 원본 추가와 강화된 DB의 업그레이드

`official_widget_writer_20261006`은 `independent_bootstrap_20261006` 뒤에 추가된 migration이다. 과거 12-table migration snapshot을 수정하지 않고 `personal_todo_items`와 `personal_memos`에 같은 scope column/CHECK/FK와 statement trigger를 추가한다. 기존 ID·내용·사용자 ACL·URL·응답은 유지한다. 플랫폼 outbox나 새 worker를 추가하지 않는다.

migration은 DBAPI autocommit과 READ COMMITTED 이외의 isolation을 거부하고, ownership 행의 `FOR UPDATE`를 DDL 종료까지 유지한다. 기존 12개의 trigger가 정확한 table/event/scope/활성 상태로 단일 guard를 쓰는지 확인한다. 기본 cooperative guard는 그대로 새 두 table에 연결된다. 이미 역할 guard로 강화한 DB에서는 **draining** 상태만 허용하며 private SECURITY DEFINER/search-path 계약도 확인한다. 혼합·disabled·변조 상태는 자동 수리하지 않고 전체 transaction을 거부한다. 기존 principal의 권한과 owner/generation/artifact는 migration으로 바뀌지 않는다.

강화된 12-table DB의 명시적 준비 순서는 다음과 같다. 이는 내부 core helper의 검증된 경계이며 운영 자동 전환 명령이나 서비스 활성화 승인이 아니다.

1. 새 쓰기 접수와 잔여 source writer를 중단하고 기존 exact snapshot으로 drain한다. migration/controller는 원본 DML과 분리된 transaction을 사용한다.
2. migration을 적용하여 14개가 모두 동일한 role guard를 사용하게 한다. 기존 역할의 동일 `prepare_principal` 재요청은 원래 매핑만 반환하며 두 table의 권한을 추가하지 않는다.
3. 사전 준비한 **새 LOGIN**에 다음 generation/artifact를 고정해 `prepare_principal`을 명시 호출한다. 현재 관리자·원본 세션과 예상 외 권한을 재검사한 후 현재 14개 source의 DML 권한만 부여한다. 기존 NOLOGIN owner로 `install_role_guard`를 호출해 전체 inventory를 확인한다.
4. 이전 principal을 명시 회수하고 실제 새 연결·제한 권한을 검증한 뒤 exact draining snapshot에서 다음 legacy generation으로 CAS한다. 이전 역할/GUC/재접속은 새 세대를 자동 채택하지 않는다. `official-suite` owner 활성화는 계속 거부된다.

migration이 ownership을 잠근 동안 잔여 transaction이 새 두 table과 기존 table을 반대 순서로 쓰면 DDL 대기나 deadlock이 발생할 수 있다. 먼저 writer를 drain/중단하고 PostgreSQL이 거부한 **전체 migration transaction**을 rollback한 뒤 현재 schema/ownership부터 재확인한다. 부분 DDL commit, 잠금 우회, 자동 권한 확대로 재시도하지 않는다.

cooperative schema downgrade는 두 column/constraint/trigger만 제거하고 원본 행을 보존한다. role guard를 사용 중인 schema downgrade는 명시적 retirement 없이 거부한다. **이전 호환 image로의 rollback은 schema downgrade와 별개**이며 ownership 세대·감사를 초기화하지 않는다. 위 고정 inactive image는 이 확장 이전 산출물이다. 이 revision까지의 범위는 source 14개이며 다음 Planner revision이 한 원본을 더한다. 인증/ACL·outbox·나머지 원본/worker/routing의 실제 서비스 연결은 남아 있다.

### Planner 원본 추가와 동일 transaction의 부수 변경

`official_planner_writer_20261006`은 위 Personal Widgets revision 다음에 `planner_events`를 더한다. 이전 14개 trigger의 동일 guard·scope·활성 상태와 실제 READ COMMITTED transaction을 검증하며, 강화된 DB는 draining 상태에서만 같은 role guard로 확장한다. 기존 역할 grant·owner·generation·artifact는 변경하지 않는다. 새 세대의 새 LOGIN을 명시적으로 준비한 뒤 15개 trigger inventory 확인·이전 역할 회수·exact CAS 순서를 따른다. 기존 역할 재준비는 여전히 권한을 확대하지 않는다. 앞선 12→14 migration과 그 검사의 역사적 inventory는 유지한다.

준비 함수도 이 순서를 서버에서 확인한다. `prepare_principal`은 **새 mapping/GRANT 이전**에 ownership 잠금 아래 현재 전체 source trigger의 table 집합·단일 guard·함수 schema·활성 상태·events·인자 수·고정 scope를 검사한다. 아직 14-source schema이거나 누락·혼합·변조 상태면 권한이나 mapping을 추가하지 않는다. 같은 검사를 `install_role_guard`가 재사용한다. 이미 바인딩된 principal의 정확한 replay는 기존 매핑만 반환하며 새로운 grant를 하지 않는다. migration 순서를 적은 문서만으로 권한 발급을 보호하지 않는다.

기존 HTTP와 승인된 AI 서비스의 일정 쓰기는 원본 trigger를 거친다. 원본 생성이나 기존 partition 보정이 거부되면 같은 transaction의 `retrieval_partitions`도 rollback한다. 기존 승인 요청의 원본 쓰기 없는 멱등 조회는 drain 중에도 읽기로 남는다. 일정 소유자 ACL·시간대·Calendar/Meeting 조회·AI 승인 요구는 바꾸지 않는다. 현재 Planner RAG enqueue는 no-op이며 외부 객체/queue 쓰기를 새로 추가하지 않는다. 제한 역할에 partition·인증·감사 권한을 추가하지 않았으므로 15개 source 역할만으로 전체 Planner 서비스를 실행할 수 없다.

cooperative schema downgrade는 기존 일정 데이터를 보존하며 role guard 사용 중 downgrade는 명시적 retirement 없이 거부한다. schema downgrade와 image rollback은 별개다. 기존 고정 inactive image에는 이번 변경이 없다. Diagrams처럼 DB commit 전 객체를 덮어쓰거나 삭제하는 앱은 source trigger 추가 외에 첫 외부 부작용 전 잠금·제한된 transport·불명확 결과 처리 설계가 필요하며 아직 전환하지 않았다.

### Docs 협업 연결의 writer drain

[Docs hub](../apps/api/src/miy_api/domains/docs/collab.py)는 프로세스에 고정된 `official.suite / legacy / 1 / NULL`을 사용한다. DB의 최신 세대를 읽어 오래된 프로세스나 재접속 방에 채택하지 않는다. 기존 원본 로그인·앱 admission·문서 edit ACL을 검증한 뒤, 기존 collab row를 재사용하는 GET session/WS handshake도 현재 owner의 active 상태와 정확히 비교한다. 각 송수신 frame 및 기존 주기적 ACL monitor도 다시 검사한다. 이 조회는 빠른 거절을 위한 것이며, 실제 snapshot transaction은 같은 identity를 명시적으로 bind하고 최종 DB source trigger가 commit fence를 맡는다. 오래된 snapshot으로 판단되어 DML 없이 끝나는 background 경로도 drain에서 저장 성공으로 처리하지 않는다.

정확한 writer-unavailable envelope 또는 DB guard가 감지되면 해당 room을 즉시 현재 cache에서 제거하고 WS `1013 / official_writer_unavailable`로 닫는다. dirty Yjs state는 retirement·cleanup·shutdown에서 다시 저장하지 않는다. 예전 handler의 finally는 자신이 받은 runtime과 현재 room이 같은지 확인하므로 같은 key의 새 방을 지우지 않는다. 방의 observer도 key만으로 새 runtime을 찾지 않고 자신이 속한 runtime을 확인한다. SQL thread가 진행 중일 때 debounce를 취소하더라도 transaction이 끝나기 전 flush 직렬화 잠금을 해제하지 않는다. 공용 Yjs adapter의 새 callback은 close code/reason만 선택하며 send lock 안에서 close를 호출하지 않는다. 기본값이 없는 Whiteboard의 권한 거절·동시 send 동작은 유지한다.

비동기 `wait_for`만으로 SQL thread의 종료 시간을 보장하지 않는다. snapshot 저장 전용 Connection에만 SQLAlchemy statement hook을 붙이고, 기존 `collab_cleanup_timeout_seconds`의 남은 monotonic budget으로 PostgreSQL `statement_timeout`과 `lock_timeout`을 매 SQL마다 transaction-local로 설정한다. 여러 잠금/쿼리가 실행되어도 전체 budget을 새로 시작하지 않으며 COMMIT 직전에도 갱신한다. timeout은 rollback 뒤 저장 실패로 남기고, driver SQL/파라미터를 로그에 출력하지 않는다. hook은 완료/실패 시 제거되고 commit/rollback 후 pooled connection의 설정도 원래대로 돌아간다. 이 범위는 이미 획득한 PostgreSQL 연결의 SQL 작업이다. pool 획득·최초 연결·끊어진 네트워크의 운송 계층 deadline은 기존 공용 DB 정책을 유지하므로, 전체 shutdown이 무조건 5초 안에 끝난다고 주장하지 않는다. cleanup은 진행 중인 저장과 최종 저장 시도 등 단계별 budget을 가질 수 있다.

Docs Redis payload는 고정된 writer identity를 포함한다. 다른 identity의 update·awareness는 버리고, 일치하는 payload도 자기 DB Session으로 현재 writer를 검사한 뒤 적용한다. 초기 legacy 배포의 혼합 버전 구간에서는 **writer 키 자체가 없는** 구버전 payload만 좁게 호환한다. 로컬 고정 identity가 정확히 `official.suite / legacy / 1 / NULL`이고 매 수신 DB도 동일한 active identity일 때만 허용한다. 명시적인 `writer: null`, 일부 필드만 있는 값, 잘못된 값은 호환 경로를 사용할 수 없으며 artifact가 있거나 이후 generation/official owner이면 untagged payload를 거부한다. 구버전 receiver는 추가 writer 필드를 무시하고 기존 data를 읽으므로 초기 세대에서는 양방향 wire 호환이 유지된다. 현재 DB의 새로운 세대를 구버전 payload에 부여하지 않는다.

**초기 identity를 벗어나는 전환 전에 동일 Redis 채널의 모든 구버전 Docs WS 연결·room 및 relay producer를 drain/종료하고, 다른 호스트/수동 runtime까지 남지 않았음을 확인해야 한다.** 구버전은 writer tag를 검사하지 않으므로 새 수신기의 필터만으로 혼합 세대를 안전하게 운영할 수 없다. 현재 기본 운영 Compose는 단일 `miy-prod-api` 컨테이너를 교체하지만, 이것만으로 다른 producer의 부재가 검증되는 것은 아니다. 이후 image rollback도 새 identity를 이해하는 호환 artifact로만 해야 하며 구버전을 되살리려고 generation을 초기화하거나 untagged 허용 범위를 넓히지 않는다. 이 사전조건은 운영 전환 허가나 자동 drain 구현을 뜻하지 않는다. 다른 프로세스의 drain 알림이나 relay tag를 권한으로 믿지 않으며, frame 확인과 메모리 반영 사이에 상태가 바뀔 수 있으므로 브라우저/Redis 전파는 영속 저장 성공을 의미하지 않는다. 최종 DB trigger가 거부한 편집은 원본에 반영되지 않는다.

이 범위는 backend 연결·메모리 정리다. 오프라인 편집의 영속 보관, 사용자가 새 runtime으로 복구하는 정책, 공식 서비스 WS 인증 bridge와 운영 ingress/role 전환을 완료했다고 주장하지 않는다. 저장 실패 UI는 frontend owner의 별도 검증 결과를 따른다.

### Docs frontend의 저장 실패와 로그인 경계

[Docs snapshot controller](../packages/official-suite-web/src/docs/views/useDocsCollabSnapshotSaveController.ts)는 같은 로그인에서 snapshot 요청을 직렬 실행하고, 저장 실패 시 가장 최근 편집과 Yjs 상태를 메모리에 보존한다. 이전 요청의 실패가 그동안 작성한 새 편집을 덮지 않는다. [문서 화면](../packages/official-suite-web/src/docs/views/DocsBlockContentSurface.tsx)은 한글·영문 저장 실패 안내와 명시적 재시도를 제공하며, 같은 문서가 읽기 전용으로 전환되어도 실패 안내를 유지한다. 확인된 실패가 남아 있으면 `beforeunload`에서 브라우저의 이탈 확인을 요청한다. 문서를 바꾸면 이전 controller가 자신의 문서 참조로 마지막 저장을 시도하고 새 문서의 큐와 분리된다.

[snapshot API 요청](../packages/official-suite-web/src/docs/api/docs-api.ts)은 fetch와 응답 본문 읽기 전체에 30초 deadline을 적용한다. 호출자의 abort와 keepalive를 보존하고 완료·실패 후 타이머와 listener를 정리한다. 응답 본문을 읽다가 abort된 경우도 성공으로 표시하지 않는다. timeout은 서버 저장의 실패 또는 성공을 확정하는 증거가 아니므로 편집을 남기고 저장 실패 상태로 재시도하게 한다. 다른 Docs API와 공용 HTTP client의 timeout 계약은 바꾸지 않았다.

로그인이 바뀌면 이전 요청은 새 큐의 소유권을 잃는다. 이전 응답과 대기 중인 flush가 새 로그인 큐·실패 표시를 변경하지 않으며, 멈춘 이전 요청을 기다리지 않고 새 로그인의 저장을 시작할 수 있다. 협업 편집기도 토큰 문자열을 포함하지 않는 숫자 세대로 다시 생성한다. 이전 로그인에서 시작한 session 조회와 편집기 `onChange` 콜백은 새 문서 내용이나 저장 큐에 전달하지 않는다. 이는 브라우저 상태의 세대 경계이며 이미 서버가 접수한 요청을 취소하거나 DB writer/ACL 검사를 대신하는 권한 경계가 아니다.

집중 회귀는 저장 controller·화면·실제 API wrapper의 4개 파일 **31개**를 검사한다. stalled fetch의 deadline, body abort가 성공으로 오인되지 않음, caller abort·timer 정리, 실패 후 재시도, 새 편집 보존, 이전 로그인의 완료/실패/대기 flush, 편집기 재생성·지연 session 응답·오래된 callback, 문서별 unmount 저장과 실패 안내를 포함한다. 실제 브라우저 종료 시 저장 완료는 보장하지 않는다. 오프라인 영속 저장, 화면을 떠난 뒤 실패 편집 복원, 공식 runtime으로의 재접속/활성화는 아직 구현·검증하지 않았다.

## 다음 bounded 구현 순서

1. **접수·transaction writer fence 기반.** 단일 `official.suite`의 명시된 88개 전체 source table과 frozen migration·DB trigger·core CAS·audit·현재 관리자 재검사까지 구현했다. Docs 협업의 backend drain은 아래 검증 범위까지 연결했다. 다음은 공식 runtime 재접속·실행 identity와 worker의 durable claim/attempt/generation·결과 확정 fence다. 최소 권한 DB role과 runtime identity 연결 없이 공식 owner를 활성화하지 않는다. middleware만 검사하거나 DB commit 후 owner를 확인하는 방식은 허용하지 않는다.
2. **플랫폼 identity/admission 위임과 원본 ACL parity.** 선행 가능한 내부 HTTP bridge를 먼저 구현했다. 검증된 release/artifact/설치 generation의 명시 코어 승인, 현재 사용자·세션·회사/그룹 입장 재검사와 last-seen 없는 기존 AuthContext, Docs/PMS 원본 ACL parity를 재사용한다. 다음에는 core 원본 권한 조회를 좁은 서버 계약/DB role로 분리하고 WS/공유 링크·검색 ACL allow/deny도 비교한다. 읽기 shadow는 읽기 전용 DB role과 모든 암묵적 쓰기 차단으로 입증하며 GET이라는 이유로 허용하지 않는다. 내부 auth resolver가 SELECT만 수행한다는 증거를 전체 업무 요청의 읽기 전용 증거로 확대하지 않는다.
3. **업무 source outbox와 역방향 쓰기 제거.** 위 projection·audit·AI 경계마다 데이터 owner를 고정하고 멱등 event/operation ID와 현재 source revision을 사용한다. 같은 DB를 유지하며 기존 FK를 보존한다. suite→플랫폼 DML을 실제 역할 감사에서 제거한 뒤 app/service DB role을 분리한다. 요청 유실·중복·순서 역전·회수 tombstone이 필수 음성 검사다.
4. **서비스 image와 worker/Beat fence.** 두 wheel·공통 lock·codec/resources를 묶은 비활성 API image는 위와 같이 검증했다. 다음은 schema/grant 호환 범위와 승인된 runtime activation 경로다. API runtime은 Docs/Whiteboard collaboration 등 공식 서비스만, 플랫폼은 identity/AI/realtime control 등 공통 서비스만 초기화한다. 공식 4개 모듈·3개 Beat publisher의 별도 비활성 profile과 소유 queue 선언은 구현했다. task ID/claim/route generation을 유지하며 실제 lease·producer/outbox·DB identity를 연결한다. 현재 `celery` 기본 queue에는 양쪽 작업이 섞여 있으므로 `-Q celery`로 두 소비자를 동시에 띄우지 않는다. 소유 queue/producer routing·lease·drain·재발행 소유를 같은 전환 단위로 고정한다.
5. **동일 routing generation의 단일 writer 전환.** 사전 검증된 artifact·schema/grant·consumer inventory를 구체적으로 검토한 후에만 활성화한다. ingress/app-ID resolver, API writer fence, worker claims, Beat publisher, source outbox cursor를 한 generation으로 전환한다. 사용자 비율로 같은 업무 객체를 두 writer에 분산하지 않는다. 이전 API/WS/job drain과 재접속 정책을 적용한다. 예상 외 기존 writer/consumer가 있거나 응답이 유실되면 상태를 조회하고 unknown으로 유지한다.
6. **원복과 소스 제거.** 신규 접수 중단→진행 작업 조회/정리→호환 가능한 이전 image/owner generation으로 CAS한다. 이미 수락한 메일/녹음/AI write는 동일 operation으로 조회한다. schema는 forward-compatible 범위만 image rollback으로 복구하며 자동 downgrade하지 않는다. 관측·rollback window 후 legacy import/handler/consumer/role grant를 제거한다.

## 검증·운영 권한

현재 검사 범위는 router 집합의 disjoint union, 기존 endpoint/operation ID/응답 계약 일치, 새 profile의 무초기화·미준비·HTTP/WS 거부, 실제 wheel/entrypoint 구성, legacy worker 등록·Beat 계약이다. 운영 서비스 시작·DB grant 변경·queue drain·배포·실제 사용자 데이터 전환은 수행하지 않았다. 위 후속 구현은 일회용 fixture에서 먼저 검증하고 운영 전환은 구체적인 결과에 대한 별도 승인을 따른다.

## DM 4개 원본 보호와 첨부 commit 경계 — 로컬 검증 완료

2026-10-07 로컬 구현·검증을 마친 범위는 `dm_conversations`, `dm_conversation_participants`, `dm_messages`, `dm_message_attachments`다. 이 당시 보호 범위는 19/88이었으며 현재는 아래 후속 변경으로 88/88이다. 이전 migration 20개를 보존하고 등록 위임 head 뒤에 frozen 15→19 migration을 추가했다. 최종 실제 PostgreSQL 통합 218 PASS·외부 MinIO 1개 제외, 입력 99개 불변·소유 임시 컨테이너 정리와 독립 리뷰를 확인했다.

DM 첨부는 기존 row flush→object put→commit 순서를 사용한다. 원본 trigger가 첫 외부 put 전에 같은 ownership row의 공유 잠금을 잡는지, 진행 중 업로드 동안 drain CAS가 기다리는지 실제 PostgreSQL과 합성 object client로 확인한다. 메시지·sequence·읽음·첨부 연결의 원자적 rollback, 현재 membership ACL, commit 이후 realtime 발행, 새 key의 보상 정리를 함께 검증한다. 이미 접수한 전송이나 보상 삭제 실패를 원본 trigger 하나로 해결했다고 표시하지 않는다.
