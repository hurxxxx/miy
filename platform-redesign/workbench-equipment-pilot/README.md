# Workbench 장비·비품 관리 앱 시범 작업

비개발자인 대리급 사용자가 대략적인 업무 지식을 가지고 Workbench에서 앱을 만들어 가는 과정을 관찰한다. 실제 브라우저와 native Codex 세션을 사용하며, 생성·개발·등록·미리보기까지 이어지는 작은 대표 흐름을 확인한다.

**현재(2026-10-11):** 기존 시범 코드를 보관한 뒤 새 managed 작업에서 native 개발·포털 미리보기·MR117 필수 CI/리뷰·dev 병합·feat4 안정된 개발 앱 실행·정리를 실제 확인했다. MR121/r21의 관측 복구 후 원 요청의 명시적 계속으로 정리를 완료했으며, 임시 DB/역할·런타임·SDK·컨테이너·worktree·브랜치 부재와 안정된 개발 앱·데이터 보존을 독립38항목으로 확인했다. 운영자 지원 단일 소유자의 대표 흐름 범위다. 의미 검색(임베딩 서버 없음)·일반 직원 계정·완전 자가 온보딩·다중 사용자·운영 rollout은 미검증이다. 상세 실제 근거와 실패 이력은 [배포 인수 기록](../WORKBENCH_WORKSPACES_DEPLOYMENT.md), 이 디렉터리의 요약은 [STATUS.md](STATUS.md)가 소유한다.

## 역할과 범위

- 비개발자 역할은 원하는 업무와 확인한 화면 결과를 설명한다. 서버 경로·실행기·인증·배포 설정을 직접 구성하는 역할은 맡기지 않는다.
- 운영자는 기존 공개 진입점으로 허용된 개발 공간과 실행 환경을 준비한다. Root가 실제 브라우저·native 세션·등록 대상과 안전 경계를 확인한다.
- LLM은 필요한 업무 결정을 짧게 확인하고, 선택한 앱과 환경의 계약을 지켜 실제 작업한다. LLM의 완료 설명만으로 결과를 인정하지 않는다.
- 데이터는 가상 사람·장비·대여 기록만 사용한다. 기존 사용자 데이터·앱은 수정하지 않으며 별도 원격 서버의 프로젝트는 대상이 아니다.
- 이번 시범은 단일 소유자 개발 설치다. 가상 직원은 앱 안의 테스트 기록이며, 실제 직원 계정·전사 공개·다중 사용자 Workbench 구현을 뜻하지 않는다.

대리급 비개발자는 자연어·업무 지식·화면 조작의 역할 시뮬레이션이었다. 실제 정상 Core 개발 로그인은 기존 administrator 계정이므로 일반 직원의 자가 등록 권한을 확인한 실험은 아니다. 계정 생성·권한 변경·메일 발송은0이다. 최종 판정은 **운영자 지원 단일 소유자 개발 시범과 필수 공용 보완 확인 완료**이며, 완전 자가 온보딩·일반 직원 권한·공개 운영은 미검증/후속이다.

기존 공개 Workbench와 운영 플랫폼 연결은 보존한다. 최초 loopback Workbench의 fresh SQLite/schema0008·native 비밀번호 로그인200·shell 로드/page errors0을 실제 Chromium에서 확인했다. 현재 시범 Workbench/포털의 접속 호스트는 `localhost:19369`/`localhost:19401`, 앱 runtime은 `127.0.0.1:19403`으로 분리했다. 실제 인수에서는 localhost의 Workbench native 쿠키가127 앱에 전달되지 않았고, 알려진 bearer가HTTP URL에 없음을 확인했다. 미로그인/포털 bearer의 앱 사용·앱 bearer의 임의 존재하지 않는 설치 사용은 각각401이었다. 시범 상태 공간은 `/home/user/.local/share/miy-codex-console/pilots/equipment-20261010`이다. 지정 소스 공간 `/home/user/projects/miy-apps/workbench-equipment-pilot`은 native AI가 업무 코드를 구현·로컬 저장했고 운영자는 필요한 공개 계약 문서의 정확한 파일만 추가했다. 별도 정상 계정을 만들거나 변경하지 않았으므로 같은 설치의 외부 정상 사용자403은 확인하지 않았다.

시범 전용 Core API `172.17.0.1:19400`는 development 상태다. 별도 앱 데이터 PostgreSQL은 새 전용 볼륨/loopback으로 분리했고 읽기 전용12개 확인에서 RLS 강제·actor 없는/임의 actor 조회0·owner 원본 연결·bounded role·다른DB 연결 거부·PUBLIC 연결 없음 등을 확인했다. 실제 native 계획·승인된 개발/로컬 저장·등록·새 플랫폼 빌드/배포·대표 브라우저 업무를 단계별로 확인했다. 기존 데이터 클러스터의 설정 변경과 공개/운영 배포는 수행하지 않았으며 Root/협업 에이전트의 앱 사업 코드 쓰기는0이다. 공용 Workbench 소스와 로컬 정적 산출물은 수정했으므로 공개 서비스가 해당 산출물을 읽는지까지 확인한 것으로 확대하지 않는다. 이 작은 시범을 모든 인증/공격 경계·일반 앱의 완성으로 확대하지 않는다.

Bound 개발 SDK는 source RW·Git metadata RO·SDK RO·빈 home·private network 경계를 실제 관측했다. 반면 소스 연결 전 host 읽기 전용 계획은 단일 소유자가 신뢰한 native coding client이며 host private 파일 읽기를 물리적으로 차단하는 환경이 아니다. 앱 전용 skills 차단/짧은 맥락은 물리적 격리를 대신하지 않는다. 현재 관측에서 즉시 Core 권한 우회/SDK 누출은 발견하지 않았지만 침투 테스트는 하지 않았으며 다중 사용자 전에 별도 격리 설계가 필요하다.

현재 시범은 운영자가 준비한 실행기/개발 대상 연결을 사용한다. 미리보기 사용 동의 뒤 운영자가 앱별 보호 허용을 수동으로 연결했으며 사용자 UI/모델/소스에는 token을 전달하지 않았다. 이 반복 인계는 완전 비개발자 자가 서비스의 핵심 공백이다. 관련 UI/설계는 미완료이며 토큰 복사 UI나 최초 등록 허용 자동 승격으로 우회하지 않는다.

필수 구조와 실제 치명적 장애만 수정한다. 앱 기능 확장·화면 고도화·반복 모델 평가는 별도 개선으로 남긴다. 작업 중 기존 `BROWSER_ACCEPTANCE` 및 다른 진행 문서는 이 묶음의 편집 대상이 아니다.

필수 공용 보완은 로컬 소스 저장/typed tools·이전 native 계획의 읽기 전용 참고, 앱 전용 기존 하네스 차단/변하지 않은 검사 재사용, 비개발자 프로젝트·소스 기본 입력/배포 다음 행동, 앱 공개 계약 안내/일반 record key, artifact 권한/선언된 첫 UI 준비 gate였다. SDK source bind 시작 장애는 별도 실행기 운영 보완이었다. Manifest와 소유 generator·고정 builder/SDK·등록 원본 계약을 통해 새 앱을 연결했고 포털의 앱별 정적 import/router를 추가하지 않았다. 각 후보/실제 적용 범위는 별도 기록하며 공용 계약을 두 번째 수동 목록으로 복제하지 않는다. 이번 운영자 지원 단일 소유자 시범의 필수 인수 잔여는 없고 개별 앱 고도화는 후속으로 남긴다.
