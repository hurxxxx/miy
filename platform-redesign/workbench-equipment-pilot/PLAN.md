# 장비·비품 관리 앱 시범 계획

기준: 2026-10-10 UTC. 운영자 연결을 사용한 native 앱 구현/로컬 저장·등록·같은 HEAD의 새 플랫폼 빌드/배포 뒤 실제 대표 업무 1회와 PostgreSQL 읽기 전용12개 확인을 마쳤다. 브라우저 확인43개TRUE·별도 정상 계정2개NULL이므로 결과는 `passed_with_unverified_secondary_account`다. 아래 최초 예상/당시 기록과 현재 확인 범위를 구분하고, 대화 원문 없이 [OBSERVATIONS.md](OBSERVATIONS.md)에 결정과 결과만 요약한다.

요구 질문/초기 계획/개발 승인/후보 검사의 미완료 표현은 **그 당시 단계 기록**이다. 최종 결과는 이 문서의 '실제 묶음 결과와 남긴 한계'와 STATUS를 기준으로 읽는다. 완료 범위는 운영자 지원 단일 소유자 시범이며 실제 일반 직원의 권한/완전 자가 서비스 인수는 아니다.

## 사용자와 최초 요구

사용자는 대리급 비개발자다. 회사에서 노트북·모니터·주변 장비를 관리한 경험이 있고, 현재 누가 무엇을 가지고 있는지와 반납 예정일을 쉽게 확인하고 싶다. 물품 등록·수정, 대여·반납, 지난 기록을 한 화면에서 관리하는 앱을 기대한다. 데이터베이스·서버·SDK·배포 방법을 알고 있다고 가정하지 않는다.

초기 설명의 빠진 부분을 LLM이 모두 임의로 정하지 않는다. 업무 결과를 바꾸는 아래 결정만 확인하고, 일반 화면 구성·개발 방법은 기존 플랫폼 계약 안에서 처리한다.

| AI가 확인할 업무 결정 | 예상 도메인 답변 요약 | 좁힌 기준 |
| --- | --- | --- |
| 개별 장비와 수량으로 관리하는 소모품의 구분 | 먼저 번호가 붙은 노트북·모니터·재사용 장비를 관리 | 한 물품을 한 건으로 관리. 소모품 입출고·구매는 후속 |
| 이번 앱을 사용할 사람과 기록할 사람의 구분 | 시범에서는 담당자 한 명이 가상 직원에게 대여한 기록을 관리 | 실제 계정은 소유자 개발 설치로 제한. 가상 직원 기록은 로그인 권한이 아님 |
| 대여할 때 필요한 정보와 동시에 가능한 대여 수 | 직원·대여일·반납 예정일을 남기고 같은 장비는 한 명에게만 대여 | 반납 전 중복 대여 거부. 예정일은 반납 상태와 구분 |
| 사용 중인 장비를 수정·삭제할 때의 처리 | 이름·위치·메모는 수정할 수 있지만 대여·반납 이력은 남김 | 대여 중 삭제 거부. 이력 있는 물품은 보관 종료로 표시하고 이력 유지 |

답이 다르면 구현 전에 기준을 갱신한다. 사용자에게 포트·프로세스·인증 키를 묻는 대신 운영자가 준비한 대상과 접근 가능 상태를 제공한다.

실제 native 질문/답변에서는 담당자 한 명이 가상 직원을 기록하고, 물품을 개별 관리하며, 처음 물품은 직접 등록하기로 했다. 반납 예정일은 선택 항목이고 직원 이름에 부서를 선택적으로 남긴다. 전체 이력을 유지하고 중복 대여·대여 중 삭제를 거부하며 반복 반납으로 이력을 중복 생성하지 않는 기준도 확인했다. 답변 UI200은 해당 시점의 요구 전달 근거이며 이후 구현·현재 업무 인수와 구분한다.

후속 질문/답변200에서는 담당자 한 명·100대 이하를 첫 규모로 정하고, 관리번호는 직접 입력하되 중복을 거부하기로 했다. 이력 있는 물품은 보관 종료로 남기고 한 번도 사용하지 않은 물품만 삭제한다. 사용자는 이 기준으로 첫 계획 확정을 요청했다. 그 요구 확인만으로 이후의 별도 구현 승인·코드 실행을 대신하지 않는다.

## 이번 최소 앱

- 물품의 최초 예상: 관리번호, 이름, 종류, 보관 위치, 메모, 사용 가능/대여 중/보관 종료 상태. 최종 최소 구현에서는 별도 보관 위치 필드 대신 메모를 사용하므로 보관 위치 기능을 구현 완료로 쓰지 않는다.
- 가상 직원: 테스트용 식별자와 표시 이름, 선택적으로 부서. 실제 직원 개인정보를 가져오지 않는다.
- 기본 CRUD: 새 물품 등록·목록/상세 조회·정보 수정·미대여/이력 없는 물품 삭제. 이력이 있으면 보관 종료로 처리한다.
- 대여: 물품·가상 직원·대여일을 기록하고 반납 예정일은 선택적으로 남긴다. 사용 가능한 물품만 한 번 대여할 수 있다.
- 반납: 열린 대여를 종료하고 물품을 다시 사용 가능으로 표시한다. 같은 대여를 다시 반납해도 이력을 중복 생성하지 않는다.
- 이력: 대여·반납 결과를 유지하고 물품별로 확인한다. 상태 변경과 이력이 어긋나지 않아야 한다.

기준은 LLM이 사용자에게 업무 용어로 요약해 확인한다. 바코드·알림·승인 결재·구매·감가상각·대량 가져오기·통계 대시보드는 이번 범위에 넣지 않는다.

최초 native 계획1/revision1은 생성됐고 해당 Task는 idle/pending0이다. 계획에는 물품 번호를 안전하게 한 번만 등록하기 위한 일반 데이터 키의 조건부 생성/조회가 필요하다는 제안이 포함됐다. 이 공용 기능의 최소 후보는 서버의 기존 PK·RLS·버전 검사를 유지해야 하며 장비 앱에만 맞춘 특별 동작을 만들지 않는다. 후보와 실제 새 앱 사용 결과는 구분한다.

공용 key 후보9PASS에서는 같은 담당자·설치·컬렉션의 현재 같은 키 행을 한 번만 만들고 중복은409로 거부한다. 조직 전체 번호의 고유성이나 영구 요청 이력을 보장하는 계약은 아니다. 삭제 후에는 다시 만들 수 있으므로 앱은 확인한 업무 기준대로 이력 있는 물품을 삭제하지 않고 보관 종료로 남겨야 한다. 실제 전용 Core 반영·앱 사용은 별도 인수다.

개발 승인 단계에서는 후보/공개 안내를 전용 Core에 반영해 native OpenAPI200·by-key 경로 있음과 개발 포털 health200을 확인했다. Native 모델도 갱신된 계약의 key 지원을 확인하고 새 개발 Task의 최종 native 계획revision1을 만들었다(Workbench 저장 revision2). 담당자 한 명/100대 이하·직원 직접 입력·등록/대여/반납/전체 이력·archive 범위는 바꾸지 않았다. 사용자는 실제 Workbench의 실행 버튼과 승인 dialog에서 `ask`로 명시 승인했고 implement POST200 뒤 Task가 running/implement가 됐다. SDK는 `ask`만 허용하며 `yolo` 선택은0이다. 이후 개발·등록·새 빌드/배포·실제 대표 업무1회까지 확인했으며 세부 기능 전체나 일반 직원 권한 인수를 뜻하지 않는다.

착수 때 준비 상태는 허용 소스 roots0·executor configured0이며 개발 포털과 Workbench 연결 대상 차이도 발견됐다. 이후 별도 환경·native 개발/로컬 저장·등록·새 빌드/배포·대표 업무 묶음까지 확인했다. 최초 준비를 비개발자가 자연어로 우회하도록 만들지 않는다. 최신 결과와 미검증 한계는 [STATUS.md](STATUS.md)를 기준으로 읽는다.

## 시범 환경과 개발 기록의 최소 보완

아래는 준비부터 개발/저장까지의 **당시 단계 기록**이다. 각 단락의 질문 대기·미완료는 그 시점의 상태이며 최신 단계는 STATUS와 가장 뒤의 OBS를 따른다. 최초 실패·후보 검사·이후 실제 적용을 지우거나 하나의 성공으로 합치지 않는다.

기존 공개 Workbench/운영 연결을 바꾸지 않고 별도 시범 Workbench를 localhost·새 SQLite·개발 MIY 대상으로 준비한다. Native 인증은 기존 경로를 사용한다. 최초 baseline은 loopback Workbench 로그인200·shell/page errors0과 지정 빈 root 생성이었다. 현재 해당 root의 기본 템플릿 소스 준비200을 확인했지만 `business.py`는 기존 placeholder 그대로이며 장비 업무 코드는 아직 없다. 운영자가 앱 업무 코드를 대신 작성한 결과로 쓰지 않는다. 운영자가 준비한 경로·실행기·대상을 비개발자가 서버 설정으로 다시 입력하게 하지 않는다.

전용 Core API/포털은 development 상태로 준비됐으며 기존 개발 registry를 사용한다. 앱 데이터는 새 PostgreSQL/전용 볼륨과 loopback으로 분리하고 기본 PUBLIC 연결/임시 객체 권한을 회수했다. 보호 설정은 host에서만 사용한다. 기존 개발/운영 설정·서비스와 이전 데이터 클러스터는 변경하지 않았다. 등록 원본과 새 앱 데이터 저장소는 역할이 다르며 실제 앱 연결/권한 결과는 별도 인수한다.

실제 추가 발견은 개발 순환의 선행조건 충돌이다. 개발 후 소스는 dirty인데 최초 등록은 clean HEAD를 요구한다. 당시 checkpoint도 최초 등록 허용을 요구해 개발 기록을 먼저 만들 수 없고, 300초 허용 기한을 개발 전체 시간에 맞출 수도 없었다. 이 실패는 [OBS-002](OBSERVATIONS.md#관측-이력)와 IMP-004로 기록한다.

최소 보완은 **현재 소유자의 앱 소스에 로컬 저장 기록을 만드는 행동**과 **플랫폼의 최초 등록 허용**을 분리하는 것이다. 로컬 저장 기록에 소유자·현재 앱/소스 연결·변경 범위·manifest·기존 Git 계약을 유지하고, 원격 게시/최초 등록/배포 권한을 주지 않는다. 실제 등록 시점에는 기존 clean HEAD·현재 원본·단기 등록 허용을 그대로 검증한다. 설계·코드 검사와 실제 UI 적용 결과를 별도로 기록하며 아직 해결 완료로 쓰지 않는다.

소유 에이전트의 로컬 후보 직접 재확인은53PASS였다. 가상 fixture에서 dirty 소스→승인된 로컬 checkpoint→clean HEAD→새 등록 동의 흐름과 pinned native 도구 스키마를 확인했고 실제 등록은 하지 않았다. 기존 등록/배포 허용·기한·권한과 Git 읽기 전용 경계는 유지한다. 실제 시범 서비스 반영·새 Task/native 실행은 운영자의 다음 인수이며 이 검사 결과로 대신하지 않는다.

실제 새 앱 프로젝트 화면에서 업무명·대략 요구만 입력한 뒤 시작했지만 앱 ID와 `reuse_notes`의 HTML required에 막혀 프로젝트 POST/Task/메시지가 모두0이었다. 이 baseline은 앱 ID·저장소·허용 경로 등의 기술 입력을 비개발자 흐름에서 검토할 근거다. 사용자에게는 업무 이름과 준비된 선택지를 제공하고, 자동 기본값과 운영자 준비를 구분한다. 로컬 저장소 식별자를 제공하는 경우 실제 원격 저장소 생성·백업 성공을 뜻하지 않는다는 사실을 표시한다. 현재는 소유 에이전트가 최소 수정 중이며 최종 적용 성공을 가정하지 않는다.

개발 설치의 배포가 연결되지 않은 경우 다음 행동을 숨기지 않는 최소 UI 후보는 검사6PASS·타입/빌드PASS다. 배포 계획은 disabled로 표시하고 소유자의 미리보기 사용 동의 후 관리자 연결을 요청하도록 안내한다. Stale/unavailable 상태에서 현재 준비 완료를 추정하지 않으며 실제 시범 브라우저 인수는 아직 없다. 완전한 비개발자 자가 배포 동의/보호 허용 인계 UI는 별도 개선이다.

## 작업 맥락에 넣을 최소 계약

1. 현재 작업은 새 시범 개인 앱과 지정 개발 설치에만 적용한다. 기존 사용자 데이터와 운영 설치는 쓰지 않는다.
2. 로그인·실행자·설치 입장·데이터 접근은 서버가 결정한다. 가상 직원 이름이나 LLM의 판단을 권한으로 쓰지 않는다.
3. 기존 manifest·SDK·소유 빌더/등록 진입점을 사용한다. 앱 추가를 위해 포털에 앱별 정적 import/router를 넣지 않는다.
4. Bound 개발 코드는 승인된 앱 소스 공간의 격리 SDK에서 실행하며 호스트 자격증명·Docker 소켓·전체 플랫폼 설정을 앱 실행 환경에 넘기지 않는다. 소스 연결 전 host 읽기 전용 계획은 단일 소유자가 신뢰한 native client이고 private 파일 읽기의 물리적 차단은 없다. 두 환경의 보장을 혼동하지 않는다.
5. 등록은 실행·배포 성공이 아니다. 현재 소스와 실제 도구/설치 상태를 확인하며 오류·unknown 결과를 성공으로 바꾸지 않는다.

기존 광범위 skills·일반 작업 체크리스트를 통째로 참고 맥락에 넣지 않는다. 실제 장애를 만난 경우에만 해당 계약의 현재 소유 진입점을 추가한다.

## 최초 검증 묶음

앱의 최소 후보가 준비되면 다음을 한 묶음으로 수행한다. 작은 수정마다 전체 검사를 반복하지 않는다. 실패를 고친 뒤에는 그 실패와 직접 영향 경계만 재확인한다.

| 범위 | 확인할 결과 |
| --- | --- |
| 대표 업무 흐름 | 가상 물품·가상 직원 준비 → 조회/수정 → 대여 → 새로고침 후 대여 상태 유지 → 반납 → 가용 상태/이력 유지 → 별도 미사용 물품 삭제 |
| 중요한 중복 경계 | 이미 대여 중인 물품의 두 번째 대여가 거부되고 열린 대여/이력이 하나로 유지. 반복 반납으로 이력 중복 없음 |
| 권한 경계 | 미로그인 또는 허용 대상 밖의 별도 테스트 실행자가 이 시범 앱/데이터를 사용할 수 없음. 실제 준비된 테스트 신원만 사용하고 기존 계정을 바꾸지 않음 |
| 데이터·화면 연결 | 실제 등록 설치·iframe·SDK·앱 데이터가 같은 새 테스트 앱에 연결. 재조회 결과와 화면 상태 일치 |

이 시범을 통과해도 전체 자연어 개발 E2E, 여러 사용자 운영, 모든 물품 업무의 완성을 주장하지 않는다. 실제 코드·공용 계약 변경에는 해당 소유자의 영향 검사와 필수 리뷰/gate를 적용하며, 이 계획은 기존 gate를 대체하지 않는다.

## 실제 묶음 결과와 남긴 한계

최종 업무 인수는 1회였다. 앞선 관측 도구 중단3회는 업무 POST0이며 기존 ledger를 그대로 보존했다. 실제 가상 물품 등록201/동일 번호409·version 불변, 대여200/검색, 반납200/이력 유지, 새로고침 뒤 저장된 물품·이력, 동시 대여200+409/승자1명, 이전 반납 같은 요청의 재처리200/현재 새 대여 보존, 새 대여 반납200, 보관 종료/복원200·이력 유지를 확인했다. 이 흐름에서는 물품 삭제를 실행하지 않았다. 개별 편집·삭제 CRUD 전체는 후속 앱별 확인 대상이다.

미로그인401·포털 bearer 앱401·앱 bearer의 임의 존재하지 않는 설치401과 localhost Workbench 쿠키의127 앱 미전달/알려진 bearer HTTP URL 부재를 확인했다. 별도 정상 계정이 없어 같은 설치의 정상 비소유자403은 미검증이며 계정 생성/변경은 하지 않았다. 실제 PG12개 읽기 전용 확인은 현재 설치의 RLS/actor/role/다른DB 경계 등이며 모든 공격·다중 사용자·운영 공개 검사는 아니다. Source HEAD/clean 상태는 유지하고 Root/협업 에이전트는 앱 사업 코드를 대신 작성하지 않았다.

물리적 데이터는 equipment1/equipment_history5이며 동시 실패에서 남은 prepared 기록1을 포함한다. 최종 원 브라우저의 정상 SDK 재연결 후 목록/detail/history GET200에서 committed 이력은 대여2+반납2=4로 확인했고 패배한 prepared1은 UI에 노출되지 않았다. 물리적 준비 기록 합계를 화면 이력으로 오인하지 않는다. 추가 업무 쓰기/준비 기록 정리 작업을 수행했다고 기록하지 않는다.

5분 앱 세션의 만료/SDK 정리는 의도된 동작이었다. 실제 화면에서 연결 버튼을 통한 정상 재연결 뒤 exchange/me/equipment200으로 복구했고 업무 데이터 쓰기는 없었다. 자동 갱신/입력 상태 보존은 이번에 구현하지 않았으며 안전 TTL을 늘리거나 SDK/app bytes를 바꾸지 않는다.

비개발자는 업무/조작 역할의 시뮬레이션이고 실제 Core 정상 계정은 기존 administrator다. 가상 직원은 payload일 뿐 실제 직원 인증이 아니다. 기존 정상 테스트 신원으로 일반 직원 자가 등록/별도 계정 same-install403을 확인하지 않았고 계정/권한/메일 변경0이다. 운영자 지원 단일 소유자 개발 시범의 필수 인수는 완료했지만 완전 자가 온보딩·일반 직원 권한·공개 운영·다중 사용자는 후속이다.
