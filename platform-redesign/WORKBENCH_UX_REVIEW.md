# MIY Workbench 데스크톱 UX 검토와 개선안

2026년 10월 12일 검토. **현재 화면은 사용자가 앱·프로젝트·작업 환경·세션의 내부 구분을 알아야 사용하기 쉽다.** 시작 방법, 진행 상태, 필요한 결정, 이전 결과가 각각 존재하지만 한 작업의 맥락으로 연결되어 보이지 않는다. 화면을 예쁘게 정돈하는 것에 앞서 이 네 정보를 일관되게 읽을 수 있도록 해야 한다.

사용자가 지적한 핵심은 타당하다. 카드와 구분선을 추가한 현재 구성에도 **무엇이 중요한지, 어느 영역을 먼저 봐야 하는지, 다음 행동이 무엇인지**를 알려주는 정보 위계가 부족하다. 기존 계획 → 실행 → 검증 → 전달 흐름을 유지하면서 표현과 정보 배치를 개선하는 것이 적절하다.

[68개 데스크톱 장면과 개별 평가 보기](../.runtime/workbench-ux-audit-20261012/index.html). 갤러리에는 분류·검색과 제안 상태 모델의 간단한 상호작용 예시가 있다. 예시는 구현된 기능이 아니다.

## 화면의 역할과 구분 방식

### Studio는 내 작업의 현재 위치를 보여준다

상단의 주 행동은 **앱 만들기**로 두고, 본문은 아래 순서로 구분한다. 각 영역에는 제목·상태·행동이 함께 있어야 한다. 구분선만 추가하는 방식으로는 어느 영역이 중요한지 전달하기 어렵다.

1. **내 확인이 필요한 작업**: 프로젝트 이름, 결정할 내용 한 문장, 기다린 시간, 검토하기. 항목이 없으면 크게 비워 두지 않는다.
2. **진행 중인 작업**: 현재 단계, 마지막 확인 시각, 열린 질문 여부, 작업 열기. 근거 없는 완료율과 예상 시간은 표시하지 않는다.
3. **최근 결과와 프로젝트**: 최근 결과 요약, 미리보기 가능 여부, 검증 상태, 마지막 작업 시각, 이어하기.

카드의 예시는 `팀 일정 관리 / 검증 중 / 담당자 필터 추가 / 마지막 확인 10초 전 / 작업 보기`다. 내용이 없는 꾸밈용 썸네일보다 상태와 최근 결과가 우선이다. 첫 사용자에게는 하나의 시작 영역과 구체적인 요청 예시를 보여준다. 기존 소스 연결은 고급 시작 방식으로 접근할 수 있게 한다.

전역 사이드 메뉴는 하나를 유지한다. 프로젝트를 선택하면 본문의 제목과 이동 경로가 바뀌고 해당 프로젝트의 작업과 결과를 보여준다. 현재 카드 → 상세 구조는 살릴 수 있다. 지침 화면의 파일 탐색기는 문서 선택용 보조 도구로서 역할이 있으므로, 단순히 열이 두 개라는 이유로 중복 전역 메뉴와 같은 문제로 취급하지 않는다.

### 작업실은 현재 작업과 다음 결정을 유지한다

화면 상단에서 **프로젝트 → 작업 이름 → 대상 환경 → 현재 상태**를 계속 확인할 수 있게 한다. 프로젝트에서 시작한 작업은 프로젝트로 돌아갈 수 있어야 한다. 현재의 세션 목록 복귀만으로는 원래 프로젝트와의 연결이 약하다.

| 영역 | 기본적으로 보여줄 내용 | 필요할 때 펼칠 내용 |
| --- | --- | --- |
| 공통 작업 헤더 | 프로젝트·작업·대상 환경, 현재 단계, 마지막 확인, 다음 행동 | 실행 연결 진단과 작업 식별자 |
| 대화와 결정 | 요구사항, 결정할 질문, 선택의 결과, 현재 대기 요청 | 전체 에이전트 활동과 상세 로그 |
| 결과 | 앱 미리보기 또는 결과 요약, 변경 요약, 검증과 한계, 결과 버전 | 코드 차이·명령 출력·브랜치 |
| 입력 | 현재 메시지 목적, 첨부자료, 요청 전송 | 모델·추론 수준·권한 상세 |

대화와 결과의 분할은 유지하되 사용자가 폭을 조정할 수 있게 한다. 빈 결과 패널은 어떤 결과가 생기는지 알려주고, 큰 입력창은 기본 높이를 줄여 현재 결정과 최근 응답이 충분히 보이게 한다. 결과가 준비되면 결과 영역에 요약을 제공하되 사용자의 읽기 위치나 키보드 초점을 임의로 빼앗지 않는다.

### 앱 관리 센터는 운영 중인 앱을 이해하게 한다

앱 카드는 `앱 이름 / 운영 상태 / 마지막 배포 / 열린 문제 / 앱 열기`를 기본 정보로 삼는다. 변경 중인 작업이 있으면 같은 카드에서 연결한다. 아직 상태를 확인하지 못했으면 미확인으로 표시하고, 사용 허용 설정만으로 정상 운영 중이라고 표현하지 않는다.

앱 상세의 첫 영역은 운영 요약으로 구성한다. 세부 정보는 **운영과 배포 / 작업 결과 / 문제 관리 / 사용량과 예산 / 연결 설정**처럼 목적별로 구분한다. 본문 내 탭이나 명확한 섹션을 사용하고 두 번째 사이드 메뉴는 만들지 않는다. URL·소스 경로·리비전·배포 요청 ID는 기술 상세에서 확인한다.

미리보기와 운영 앱을 구분하고 각 링크 옆에 대상 환경을 표시한다. 예산은 알림 기준인지 실행 제한인지 실제 동작에 맞게 설명해야 한다. 단순히 숫자 입력란을 제공하는 것만으로는 사용자가 효과를 예측하기 어렵다.

### 작업 기록은 이전 결과를 다시 찾게 한다

제목과 시각에 **관련 프로젝트, 마지막 결과 한 문장, 검증 상태, 미리보기, 다시 이어하기**를 추가한다. 완료된 대화 전체를 읽지 않아도 결과를 식별할 수 있어야 한다. 먼저 최근 작업·확인 필요·완료·실패 필터를 제공하고, 결과 내용 검색은 저장된 결과 요약과 검색 권한을 지원하는 범위에서 검토한다.

프로젝트 안의 작업 기록과 전체 작업 기록은 같은 상태와 결과 요약을 사용한다. 사용자 표시 이름은 작업 기록으로 정리하고, Codex 원본 세션 불러오기는 별도 고급 기능으로 유지할 수 있다.

| 검증 중 | 실행 중인 검사와 완료된 검사 | 검증 상황 보기 |
| 결과 준비됨 | 변경 요약·검증 결과·미검증·미리보기 | 결과 보기 |
| 실패 | 완료된 부분·실패한 단계·보존된 결과 | 복구 또는 원인 확인 |
| 상태 확인 불가 | 마지막으로 확인한 상태·현재 알 수 없는 부분 | 기존 작업 상태 확인 |

작업 완료, 개발 환경 반영, 운영 배포는 별개의 사실이다. 결과를 만들었다는 이유만으로 운영 중 배지를 붙여서는 안 된다. 계획 검토 요청 역시 명령 실행 승인과 다른 의미이며, 화면에서 필요성을 알리는 개선이 서버 승인 범위를 넓혀서는 안 된다.

중간 결정은 **왜 지금 필요한가 → 무엇을 선택하는가 → 선택하면 무엇이 달라지는가 → 제출 후 무엇이 이어지는가** 순으로 구성한다. 권장안이 있다면 근거를 함께 제시하고 다른 선택과 직접 입력도 유지한다. 거절과 취소가 서로 다른 동작이면 각각 어떤 일이 멈추는지 버튼 가까이에 설명한다. 답변이 저장·접수됐는지 확인하고 중복 제출을 막는다.

상태 확인 불가에서는 현재의 자동 재제출 방지 원칙을 유지한다. 재시도라는 모호한 버튼 대신 기존 요청을 조회하는지, 실행을 다시 시작하는지 구분한다. 진행 정보가 오래되면 마지막 보고 시각을 표시하고 확인된 진행률만 사용한다.

2027년은 아직 미래이므로 검증된 유행으로 단정할 수 없다. 2027년을 대비한 가설은 여러 비동기 작업을 맡기고 필요한 순간에만 개입하는 사용이 늘어날 때에도, 무엇이 진행 중이고 어떤 결정이 필요한지 안정적으로 이해할 수 있어야 한다는 것이다. 이를 위해 고정된 탐색 위치, 명확한 상태, 추적 가능한 결과, 복구 가능한 결정 구조를 우선한다. 임의로 메뉴가 바뀌는 화면이나 과도한 자율 실행을 최신성의 근거로 채택하지 않는다.

## 접근성과 가독성

8개 주요 영역에서 WCAG 2 A·AA, 2.1 AA, 2.2 AA 관련 axe 검사를 수행했다. 지침 화면에서 `color-contrast` 1개 규칙, 5개 요소가 위반으로 검출됐다. 보조 텍스트의 `#64748b`와 배경 `#f4f6f8` 조합은 4.39:1로 측정되어 일반 텍스트의 4.5:1 요구에 미달했다. 나머지 7개 검사 화면에서는 자동 검출 위반이 없었다. 모든 화면에 수동 확인이 필요한 ARIA 항목이 남아 있어 접근성 준수 완료를 뜻하지 않는다. [WCAG 명암비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

대표 키보드 확인 결과는 다음과 같다.

| 확인 항목 | 결과 |
| --- | --- |
| 새 작업 창 열기 | 초점이 대화상자 안으로 이동함 |
| 새 작업 창에서 Tab 16회 | 대화상자 안에서 순환함 |
| Escape로 새 작업 창 닫기 | 원래 버튼으로 돌아오지 않고 body로 이동함. 렌더링 대기 후에도 재현 |
| 프로젝트 상세에서 목록 복귀 | 기존 프로젝트 카드로 초점 복원됨 |

중요 상태와 결정 문장은 기본 14–16px 수준의 가독성을 설계 목표로 삼고, 10–11px 메타데이터는 필요한 곳으로 제한한다. 이 크기는 디자인 제안이며 WCAG의 고정 글자 크기 규정이 아니다. 상태는 색만으로 구분하지 않고 아이콘·텍스트를 함께 사용한다.

실행 상태에는 이미 `role="status"`가 존재한다. 이를 유지하면서 질문 도착·접수·완료·연결 상실이 보조기기에 실제로 유용하게 전달되는지 확인해야 한다. 업데이트마다 초점을 강제로 옮기지 않는다. [WCAG 상태 메시지](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

키보드 초점이 고정 헤더나 입력창에 가려지지 않아야 한다. 클릭 대상은 WCAG 2.2의 24 CSS px 기준과 예외 조건을 확인하고, 자주 사용하는 동작에는 충분한 여백을 둔다. 스크린리더 실사용, 200% 확대, 모든 대화상자와 승인 상태의 초점 이동은 후속 인수 항목이다. [초점 가림 기준](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html), [클릭 대상 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## 개선 순서와 확인 기준

| 순서 | 구현 범위 | 사용자에게 확인할 변화 |
| --- | --- | --- |
| 1 | 상태 용어 통일, 질문·승인 카드, 결과 요약, 입력 자료 명칭 | 지금 작업이 어디까지 왔고 무엇을 해야 하는지 설명 없이 이해함 |
| 2 | Studio의 확인 필요·진행 중·최근 결과 구분, 프로젝트 카드, 작업 맥락 유지 | 이전 작업을 쉽게 이어가고 결과를 다시 찾음 |
| 3 | 앱 관리의 운영 요약과 세부 영역 구분, 환경 조작 계층화 | 운영 상태와 개발 상태를 혼동하지 않고 필요한 관리 동작을 찾음 |
| 4 | 고급 도구 정리, 폼·오류·가독성·키보드 개선 | 중간 오류와 반복 작업에서도 위치와 다음 행동을 잃지 않음 |

아래 수치는 **제안하는 인수 목표이며 이번 검토에서 측정한 성과가 아니다**. 대표적인 첫 사용자 5명부터 관찰하되 작은 표본을 전체 사용자 통계로 일반화하지 않는다.

- 첫 화면을 5초 본 뒤 앱 만들기·진행 작업·이전 결과의 위치를 설명한다.
- 5명 중 최소 4명이 설명 없이 기존 작업을 이어가고 최근 결과를 10초 안에 찾는다.
- 실행 중·답변 대기·결과 준비·운영 배포의 차이를 구분한다.
- 승인 전에 대상과 영향을 설명하며, 거절·취소의 결과를 이해한다.
- 연결 상실 후 같은 요청을 중복 실행하지 않고 기존 작업의 상태를 확인한다.
- 키보드로 시작·질문 응답·결과 확인·돌아가기를 수행하고 초점이 유지된다.

검토를 위해 추가한 파일은 보고서와 로컬 증거 자료다. 제품 코드 수정, 커밋, 게시, 배포는 이번 UX 검토에서 수행하지 않았다. 기존 작업 중이던 소스 변경은 보존했다.
